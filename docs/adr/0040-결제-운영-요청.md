# ADR-0040 결제 운영(확정 · 취소)은 ERP 화면에서 요청하고 Payment가 5분마다 가져가 검증 · 실행한다

- 상태: 결정
- 날짜: 2026-11-24
- 관련 시스템: Payment Server, ERP
- 대체: ADR-0038, ADR-0039

## 맥락
- ADR-0038(운영 취소)과 0039(MANUAL_REVIEW 운영 확정)는 전산 담당자가 **Payment에서 직접** 실행하도록 했다. 담당자는 ERP(목록 · 처리 기록)와 Payment(확정 · 취소) 두 곳을 써야 하고, Payment에 운영 화면이 필요해진다.
- ERP는 다른 시스템을 호출하지 않고(ADR-0024), 결제 데이터의 주인은 Payment다(ADR-0023). 그래서 ERP가 Payment를 고치라고 보낼 수 없다.
- Payment → ERP 요청은 허용된다 (ADR-0024). Payment는 이미 5분마다 ERP로 결제 상태를 보낸다 (ADR-0025).
- PAYMENT-SIMULATOR 코드 확인: VAN 취소 전문에는 카드번호가 없고, 카드번호는 `/cancel` 입구의 본인 확인 정책이다 (ADR-0038 맥락). 결과를 모르는 승인은 그대로 취소할 수 없고, 먼저 사실을 확인해 확정해야 한다 (ADR-0039 맥락).
- 바뀌지 않은 내용은 이 ADR에 다시 적는다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| Payment에서 직접 실행 (ADR-0038 · 0039) | 즉시 반영 | 운영 화면 두 곳. Payment GUI 필요 |
| ERP 화면에서 요청, Payment가 가져가 실행 | 담당자 화면 하나. Payment GUI 불필요. 규칙 유지(Payment가 묻고 자기 DB를 고침) | 최대 5분 지연. Payment에 요청 수집 · 검증 기능 추가 |

## 결정
- **고객 반품은 결제 카드 지참 필수**, 결제 포기 시 보상 취소는 카드를 다시 읽는다 (유지).
- **운영 작업은 ERP 화면 하나에서 한다.** 전산 담당자가 ERP에서 다음 운영 요청을 만든다. ERP DB에 "운영 요청(대기)"으로 저장된다.
  - **운영 확정:** `MANUAL_REVIEW` 건을 VAN · 카드사에 **전화 · 메일로 확인**한 결과(승인됨 / 거절됨 등)와 근거(문의처 · 일시)를 입력 (ADR-0039 유지).
  - **운영 취소:** 돈이 빠졌지만 어떤 확정 판매에도 쓰이지 않은 승인을 카드 없이 취소 (ADR-0038 유지). ERP는 조회 시점의 최신 데이터로 반환 대상인 건에만 요청을 허용한다.
- **Payment가 가져가 실행한다.** Payment는 **5분마다** ERP에 "나에게 온 운영 요청"을 요청해 받는다 (상태 전송 주기와 함께).
  - Payment는 실행 전에 **자기 데이터로 검증**한다: 대상 거래 존재, 현재 상태가 요청과 맞는지(운영 확정은 미확정 건만, 운영 취소는 확정 승인이고 성공한 취소 · 망취소가 없는 건만), 금액. 맞지 않으면 거부하고 사유를 남긴다.
  - 운영 취소는 저장된 원승인 정보로 VAN에 보낸다 (카드번호 불필요).
  - 요청자 · 사유 · 근거 · 결과를 Payment 감사 로그에도 남긴다.
- **결과는 기존 경로로 돌아온다.** Payment 상태 변경 → 아웃박스 → 5분 전송(ADR-0025)으로 ERP에 반영되고, ERP는 그 운영 요청을 완료 / 거부로 표시한다. 대사 불일치는 다음 대사에서 해소된다.
- **ERP 처리 기록:** 운영 요청과 그 결과가 처리 기록이 된다 (담당자 · 처리 업무 · 메모 · 일시, 감사 로그). 조치가 필요 없는 건은 담당자가 "조치 불필요"로 기록한다.
- **즉시 조회는 그대로** 전산 담당자가 Payment 운영 조회(읽기 전용 API)로 한다 (ADR-0026). Payment GUI는 두지 않는다.
- 2인 승인은 두지 않는다 (ADR-0038 유지).

```text
담당자 ─ ERP 화면: 운영 요청 입력 ─▶ ERP DB (대기)
Payment ─ 5분마다 "내 운영 요청?" ─▶ ERP          (Payment가 묻는 방향)
Payment ─ 자기 데이터로 검증 → 확정 / VAN 취소 실행
Payment ─ 5분 상태 전송 ─▶ ERP: 요청 완료 · 대사 해소
```

## 대가와 후속 작업
- 운영 요청은 최대 5분(가져가기) + 5분(결과 전송) 뒤에 ERP에서 완료로 보인다.
- ERP가 뚫리면 가짜 운영 요청이 생길 수 있다. Payment는 자기 데이터 검증으로 "판매와 무관하게 상태가 맞지 않는 요청"은 막지만, "판매에 쓰인 승인인가"는 ERP 판단을 믿는다. ERP 권한 · 감사로 막는다.
- PAYMENT-SIMULATOR 과제: 운영 요청 수집(5분) · 검증 · 실행(운영 확정 / 운영 취소), 감사 로그. ERP 과제: 운영 요청 등록 화면 · 대기 목록 응답 API · 반환 대상 판단.

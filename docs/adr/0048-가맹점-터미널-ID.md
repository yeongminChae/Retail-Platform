# ADR-0048 터미널 ID는 POS에, 가맹점은 터미널로 정하고, 취소는 같은 터미널이 기본이며 가맹점별로 교차 취소를 허용한다

- 상태: 결정
- 날짜: 2026-11-27
- 관련 시스템: POS_APP, Payment Server, ERP
- 관련: ADR-0031 (반품 창구), ADR-0040 · 0047 (운영 취소), ADR-0042 (주기 통신 추가), backlog "가맹점 ID · 터미널 ID"

## 맥락
- backlog: 승인에 가맹점 ID · 터미널 ID를 기록하고 취소 시 검증한다. 반품은 원래 판매 POS가 아니라 고객센터 POS에서 일어난다 (ADR-0031).
- 가맹점 ID와 터미널 ID는 우리 점포코드 · POS 번호가 아니라 카드사 · VAN이 발급한 번호다 (**가정**, 국내 오프라인 결제의 일반적인 구조).
- 교차 취소 참고 사례 (**확인, 원문 미열람**): KIS정보통신 VAN 서비스 이용약관 제9조. 웹 검색 결과 요약 기준으로, 원문 · 개정일은 직접 확인하지 않았다.
  - 단말기로 승인받은 거래는 단말기로 취소한다.
  - 가맹점이 "POS 단말기 교차취소요청서"를 내면 가맹점 안의 모든 POS 단말기에서 교차 취소가 가능하다.
- Payment는 posTrx(ADR-0045)에서 점포 · POS를 알 수 있다. 남는 것은 점포 · POS → 터미널 · 가맹점 연결표다.
- 점포 · 기기 기준정보의 원본은 ERP다 (ADR-0011).
- 카페 · 소상공인 매장은 한 점포에 사업자가 여럿일 수 있다 (backlog).

## 선택지
| 항목 | 선택지 | 장점 | 단점 |
|---|---|---|---|
| 관계 | 터미널 → 가맹점 → 점포 (v1 점포당 가맹점 1) | 한 점포 여러 사업자로 확장해도 로직 그대로 | 테이블 둘 |
| | 점포 → 가맹점 직접 | 단순 | 점포 안 사업자 분리 시 다시 설계 |
| 연결표 출처 | Payment가 ERP에서 가져옴 | 원본 한 곳. 기기 추가는 ERP에만 | 주기 통신 하나 추가 |
| | 점포 서버가 승인 요청에 실음 | 추가 통신 없음 | Payment가 값을 확인할 수 없음 |
| 취소 터미널 | 같은 터미널 기본 + 가맹점별 교차 취소 설정 | 참고 사례와 같은 구조. 가맹점마다 정책 선택 | 설정 값 하나 추가 |
| | 같은 가맹점이면 항상 허용 | 단순 | 교차 취소를 원하지 않는 가맹점을 표현 못 함 |
| | 원승인과 같은 터미널만 | 가장 엄격 | 고객센터 POS 반품이 막힘 (ADR-0031 충돌) |
| 반품 창구 검증 | POS_APP (ADR-0031) | 업무 규칙은 판매 쪽에. Payment는 결제 규칙만 | — |
| | Payment도 기기 유형 검사 | 이중 방어 | Payment가 POS 업무 유형에 묶임 |

## 결정
- **관계:** 터미널 ID는 POS(판매 · 고객센터)마다 하나, 터미널은 한 가맹점에 속하고, 가맹점은 한 점포에 속한다. **v1은 점포당 가맹점 1개.** 가맹점은 터미널로 정한다 (POS → 터미널 → 가맹점). 운영 전용 POS(ADR-0047)는 터미널 ID가 없다.
- **POS는 가맹점 · 터미널 값을 보내지 않는다.** Payment가 posTrx의 점포 · POS로 연결표에서 찾는다.
- **연결표는 Payment가 ERP에서 가져온다** (Payment → ERP 요청, ADR-0024 유지). 하루 1회 전체, 그리고 5분 운영 요청 수집(ADR-0040) 때 마지막 버전 이후 변경분. ERP가 응답하지 않으면 가진 사본으로 계속 처리한다.
  - 연결표: 가맹점(ID · 점포 · 교차 취소 허용 · 사용 여부), 터미널(ID · 가맹점 · 점포 · POS 번호 · 사용 여부). 기기 유형은 넣지 않는다.
- **승인:** 등록 · 사용 중인 터미널과 가맹점이어야 한다. 아니면 VAN 호출 없이 거부한다. 승인 시점의 가맹점 ID · 터미널 ID(원승인 TID)를 저장하고 VAN에 보낸다.
- **취소 (교차 취소 정책):**
  - 가맹점 ID는 원승인과 같아야 한다.
  - **기본은 원승인과 같은 터미널(TID)에서만 취소한다.**
  - 가맹점의 **교차 취소 허용(`crossTerminalCancelAllowed`)**이 켜져 있으면, 같은 가맹점의 등록된 사용 중 터미널에서도 취소한다.
  - **Retail-Platform 점포는 고객센터 반품을 위해 교차 취소를 켠다.**
  - 원승인 TID와 취소 TID를 각각 기록한다.
  - 망취소는 같은 터미널만 허용한다.
- **역할 분리:**
  - "반품은 고객센터 POS에서만"은 **POS_APP**이 검증한다 (ADR-0031).
  - **Payment**는 기기 유형에 의존하지 않고 가맹점 · 터미널 · 교차 취소 권한 · 거래 정합성을 검증한다.
  - **VAN Simulator**도 자체 등록부로 교차 취소 정책을 **독립적으로** 검증한다.
- **운영 취소(ADR-0040, 0047)는 별도 권한 경로로 유지한다.** 담당자 요청 → Payment 검증으로 권한을 확인하고, 교차 취소 설정과 무관하게 원승인 TID로 VAN에 보낸다.
- 이 정책은 실제 VAN의 교차 취소 사례를 참고한 **프로젝트 설계 정책**이며, 모든 VAN사의 공통 규격이라고 가정하지 않는다.
- **주기 통신 추가 (ADR-0042 보완):**

| 경로 | 방식 | 주기 |
|---|---|---|
| Payment → ERP 가맹점 · 터미널 연결표 | 전체 1회 + 변경분 | 하루 1회 + 5분 (운영 요청 수집과 함께) |

## 대가와 후속 작업
- 새 기기는 ERP 등록 후 최대 5분 뒤부터 카드 결제가 된다. 개점 전 등록이 원칙이다.
- 실제로는 VAN이 TID 발급처이므로 VAN 등록부가 원본이고 ERP는 그 값을 입력해 둔 것이다 (가정). ERP 입력값과 VAN 등록이 어긋나면 VAN이 거절한다.
- ERP 과제: 가맹점(ID · 교차 취소 허용) · 기기 터미널 ID 입력, 연결표 전체 · 변경분 응답 API.
- POS_APP 과제: 반품은 고객센터 POS에서만 (ADR-0031, 변경 없음).
- 매입 · 정산은 가맹점 ID별로 묶는다 (PAYMENT-SIMULATOR 07). 키오스크 · 소상공인은 "점포당 가맹점 1개" 제약만 풀면 된다.

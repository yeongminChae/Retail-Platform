# ADR-0047 운영 취소는 점포별 운영 전용 POS 번호로 체번하고, Payment는 운영 요청마다 종료 신호를 보낸다

- 상태: 결정
- 날짜: 2026-11-26
- 관련 시스템: POS_APP, Payment Server, ERP
- 관련: ADR-0040 (보완), ADR-0031 · 0044 (기기 유형 · 기동 점검 추가)

## 맥락
- 운영 취소(ADR-0040)도 취소 거래라 자기 posTrx가 필요하다. 고객 반품은 반품 거래의 posTrx를 쓰지만, 운영 취소는 POS 거래 없이 본사에서 일어나 Payment가 번호를 만들어야 한다.
- 거래번호는 점포 서버가 POS별로 매긴다 (ADR-0002, 0044). Payment가 실제 POS(고객센터 POS 등)의 번호로 매기면 점포 서버와 서로 순번을 몰라 겹친다. 본사가 점포 서버에 번호를 요청하는 것은 요청 방향 원칙(ADR-0013, 0024) 위반이다.
- ADR-0040은 운영 요청의 결과가 결제 상태 전송으로 돌아온다고 했다. 그런데 Payment가 검증에서 거부하거나 VAN이 거절한 요청은 상태가 바뀌지 않는다. 그러면 ERP는 그 요청이 끝났는지 알 수 없어 대기로 남고, Payment는 5분마다 같은 요청을 다시 가져가 다시 거부한다.
- 운영 확정으로 "승인됨"을 확정한 건은 나중에 운영 취소 · 매입이 가능해야 한다. VAN 취소에는 원승인의 승인번호 · VAN 거래번호 · 금액이 맞아야 한다 (PAYMENT-SIMULATOR VAN 확인).

## 선택지
| 항목 | 선택지 | 장점 | 단점 |
|---|---|---|---|
| 운영 취소 번호 | 점포별 운영 전용 POS 번호, Payment가 매김 | 겹치지 않음. 형식 · 거래 키 묶기 · 대사가 그대로 동작 | ERP 기기 유형 하나 추가, 점포 서버에 예외 처리 |
| | 실제 고객센터 POS + 번호 구간 | 기기 추가 없음 | 점포 서버가 구간을 건너뛰어야 하고 거래가 많으면 겹침 |
| | 별도 형식(`OPS-…`) | 단순 | posTrx 형식이 둘이 됨. VAN · ERP가 두 형식을 받아야 함 |
| 결과 회신 | 종료 신호(요청 ID · 결과 · 사유 코드) | 대기 목록이 비고 반복 처리가 없음 | 메시지 종류 하나 추가 |
| | 결제 최종 상태만 | 추가 없음 | 거부 · 거절된 요청이 끝나지 않음 |

## 결정
- **운영 전용 POS:** 점포마다 실제 단말이 없는 **운영 전용 POS** 번호를 ERP 기기 정보에 등록한다. 기본 번호는 `9999`다 (Payment 설정값).
  - ERP POS 기기 유형(ADR-0031)에 **운영 전용 POS**를 추가한다. 허용 작업은 없다 (Payment의 운영 취소 번호로만 쓰임).
  - 점포 서버는 이 유형의 번호로 단말이 기동하면 거부한다 (ADR-0044 기동 점검에 추가).
  - 이 유형은 **POS 마감 대상에서 제외**한다. 점포 마감의 "전 POS 마감" 조건(ADR-0019)에 들지 않는다. 시재도 없다.
- **운영 취소 posTrx:** `점포(4)-실행일(8)-운영 전용 POS(4)-거래번호(4)-01`. 예: `1000-20261126-9999-0001-01`.
  - 점포는 원승인의 점포다. 실행일은 Payment 실행 날짜(Asia/Seoul)다. 영업일은 POS_APP 소유라 Payment가 모르므로 달력 날짜를 쓴다.
  - 거래번호는 Payment가 점포 · 실행일별로 매긴다. 운영 전용 POS의 번호는 Payment만 매긴다.
  - 형식은 ADR-0045 posTrx와 같으므로 Payment · VAN 형식 검증을 그대로 통과한다.
- **매출:** 운영 취소는 POS 판매 · 반품 판매를 만들지 않으므로 매출 집계에 들어가지 않는다. 결제 상태 메시지(ADR-0025)에서 원승인 posTrx의 취소로 `kind = OPERATION`과 함께 실린다. 대상이 판매에 쓰이지 않은 승인이므로 대사 불일치가 해소된다 (ADR-0027). 판매에 쓰인 승인을 잘못 취소하면 대사 불일치로 올라온다.
- **종료 신호:** Payment는 운영 요청마다 처리가 끝나면 ERP에 **종료 신호**를 보낸다 (Payment → ERP, 결제 상태와 같은 5분 아웃박스).
  - 내용: ERP 요청 ID, 결과(`DONE` 요청대로 반영 / `CLOSED_NO_CHANGE` 바꾸지 않고 종료), 사유 코드(선택), 대상 posTrx, 운영 취소 posTrx.
  - ERP는 종료 신호를 받은 요청을 대기 목록에서 빼고 사유를 화면에 보여 준다. 업무 판단(조치 필요 여부 · 대사)은 결제 최종 상태(ADR-0025)로 한다.
  - Payment는 같은 요청을 다시 받으면 실행하지 않고 종료 신호를 다시 보낸다.
- **운영 확정 입력:** "승인됨"으로 확정할 때 ERP는 **승인번호 · VAN 거래번호 · 금액**을 필수로 받는다. 담당자가 VAN · 카드사 확인 때 함께 받는다고 본다 (**가정**).

## 대가와 후속 작업
- 점포 서버는 운영 전용 POS 유형을 알고 기동 거부 · 마감 제외를 해야 한다 (POS_APP 레포).
- ERP 화면에서 운영 전용 POS는 일반 기기 목록 · 마감 현황에서 구분해 보여 준다 (ERP 레포).
- 운영 전용 POS 거래번호는 점포 · 실행일당 9999건이 상한이다. 운영 취소 건수로 충분하다고 본다 (가정).
- 종료 신호 · 대기 목록 API 계약은 `contracts/`에 둔다.
- PAYMENT-SIMULATOR 상세: `docs/phase2/04-운영-요청.md`.

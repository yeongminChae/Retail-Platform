# ADR-0014 판매 결과는 아웃박스에 쌓아 HTTPS로 ERP에 보내고 ERP는 거래번호로 멱등 처리한다

- 상태: 결정
- 날짜: 2026-11-18
- 관련 시스템: POS_APP, ERP

## 맥락
- 판매 확정 · 반품 · 마감 결과를 점포 서버에서 본사 ERP로 보내야 한다. 판매 흐름은 ERP를 기다리지 않는다 (ADR-0013).
- 판매 저장과 전송을 따로 하면, 저장 후 전송 전에 서버가 죽을 때 ERP에서 판매가 빠지고, 전송 후 저장이 실패하면 ERP에만 있는 판매가 생긴다.
- 본사 회선이 끊겨도 점포는 판매를 계속하므로 (ADR-0012), 그동안의 결과가 쌓였다가 나중에 가야 한다.

## 선택지
**전달 구조**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 아웃박스 + 백그라운드 전송 | 판매와 전송 기록이 한 트랜잭션이라 누락 · 유령 판매가 없음. 회선 장애 동안 쌓였다가 재전송. 점포에 추가 인프라 없음 | 재전송 순서 · 상태 관리를 직접 구현 |
| 메시지 브로커 (Kafka · RabbitMQ 등) | 현업에 흔한 이벤트 구조 | 점포마다 브로커 또는 본사 브로커 직결 — 운영 부담 |
| 일마감 배치 | 단순 | ERP 재고가 하루 늦게 반영 |

**전송 프로토콜**

| 선택지 | 장점 | 단점 |
|---|---|---|
| HTTPS | 상태 코드 · JSON · OpenAPI 계약, 추적 ID · 지표 · TLS를 그대로 씀 | 요청마다 오버헤드 (이 규모에서는 무의미) |
| 직접 TCP 전문 | 연결 유지 · 오버헤드 작음 | 프레이밍 · 응답 확인 · 재전송 · TLS · 모니터링을 직접 설계. TCP 전문은 이미 Payment Server ↔ VAN 구간에서 다룸 |

## 결정
- **아웃박스:** 판매 확정(반품 · 마감 포함) 시 판매 저장과 같은 트랜잭션으로 점포 서버 DB의 아웃박스 테이블에 전송 대상을 한 줄 기록한다.
- **전송:** 백그라운드 작업이 아웃박스를 읽어 **HTTPS**로 ERP API에 보내고, 성공 응답을 받으면 전송 완료로 표시한다. 실패 · 회선 장애 시 남겨 두고 재시도한다.
- **멱등:** ERP는 **거래번호(점포 · 영업일 · POS · 순번, ADR-0002)** 기준으로 같은 판매가 여러 번 와도 한 건으로 처리하고, 중복 수신도 성공으로 응답한다.
- 계약(OpenAPI)은 `contracts/`에 둔다.

## 대가와 후속 작업
- 재전송 간격 · 최대 지연 알림 기준, 전송 순서 보장 여부(예: 원거래보다 반품이 먼저 도착), 오래 실패한 건의 처리 절차는 미정.
- 미전송 건수는 모니터링 지표에 포함한다 (standards.md 백업 · 모니터링 항목).
- 마감 전송과 ERP 월마감 · 대사의 관계는 일마감 · 대사 설계에서 정한다.
- 오프라인 판매 확장 시 클라이언트 → 점포 서버 업로드에도 같은 멱등 원칙을 쓴다 (standards.md 3.1).

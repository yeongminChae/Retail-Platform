# ADR-0017 추적 ID는 X-REQUEST-ID로 전 시스템에 전파하고 거래번호와 구분한다

- 상태: 결정
- 날짜: 2026-11-18
- 관련 시스템: POS 클라이언트, POS_APP, Payment Server, ERP

## 맥락
- standards.md는 "추적 ID 전 시스템 전파"를 v1 포함으로 두었고, architecture.md는 미정으로 두어 두 문서가 맞지 않았다.
- PAYMENT-SIMULATOR 확인 결과 (2026-11-18, `main` 기준):
  - Payment Server와 VAN Simulator(Control Plane)는 HTTP 요청의 `X-REQUEST-ID`를 받으면 그대로 쓰고, 없으면 UUID를 생성한다. MDC `requestId`에 넣어 로그에 `[rid=...]`로 찍고 응답 헤더로도 돌려준다 (`docs/logging-policy.md`).
  - 아직 이 헤더를 보내는 호출자가 없어, 실제로는 요청마다 새 UUID가 생성된다.
  - Payment Server → VAN TCP 전문에는 별도의 `vanRequestId`를 쓰며, HTTP 요청 ID와 의도적으로 분리했다.
  - Recovery 스케줄러처럼 HTTP 요청 밖에서 도는 작업에는 MDC를 채우는 코드가 없다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| `X-REQUEST-ID` 전파 + 로그 | Payment Server가 이미 지원. 추가 인프라 없음 | 구간별 소요 시간은 로그로 계산해야 함 |
| OpenTelemetry (W3C `traceparent`) | 표준 분산 추적, 구간별 지연 그래프 | Collector · 추적 저장소 인프라 추가 |

## 결정
- **거래번호와 추적 ID를 구분한다.**
  - 거래번호(ADR-0002): 업무 추적 키. 영구 보존, 시스템 간 데이터 연결과 대사에 쓴다.
  - 추적 ID: 요청 하나의 기술 추적 키. 로그를 시스템 간에 이어 보는 데만 쓴다. 업무 데이터의 키로 쓰지 않는다.
- **헤더는 `X-REQUEST-ID`로 플랫폼 공통**이다.
- **생성:** 점포 서버(POS_APP)가 POS 클라이언트 요청을 받을 때 만든다. 클라이언트가 보내면 그 값을 쓴다.
- **동기 전파:** 점포 서버 → Payment Server 호출에 같은 값을 싣는다. Payment Server는 이미 받은 값을 그대로 쓴다.
- **비동기 전파:** 아웃박스(ADR-0014)에 원래 판매 요청의 추적 ID를 저장하고, ERP 전송 시 함께 보낸다. 기준정보 수신(ADR-0015) 같은 백그라운드 작업은 작업 실행마다 새 추적 ID를 만든다.
- **로그:** 모든 시스템이 로그마다 MDC로 추적 ID를 남긴다.
- **Payment Server → VAN 구간**의 `vanRequestId` 분리는 Payment Server 내부 결정으로 유지한다.
- **OpenTelemetry는 v1 설계에서 제외**한다. 개발 착수 전에 다시 검토한다.

## 대가와 후속 작업
- 구간별 지연은 로그 시각으로 계산해야 한다. standards.md 성능 기준 3단계(VAN 지연이 다른 POS로 번지지 않음) 검증 방법을 정할 때 OpenTelemetry 도입을 다시 본다.
- Payment Server Recovery 스케줄러의 로그 추적 ID는 PAYMENT-SIMULATOR 레포에서 정한다.

# 상용화 기준

> 상태: **초안 — 항목별 포함 여부 결정 중.**
> 이 문서가 모든 설계의 판단 기준이다. "다 됐나?"는 여기 체크리스트와 `e2e/` 시나리오 통과 여부로 판단한다.

## 0. 카드 결제 모듈이 시뮬레이터인 것에 대해

결제 쪽 상용화 수준은 **"VAN 어댑터만 교체하면 실연동이 되는 구조"**로 정의한다.

- 실제 VAN · 카드사 전문 송수신은 시뮬레이터로 대체한다 (Payment Server의 `VanGateway` 경계).
- 그 위의 거래 상태 관리 · 멱등성 · 조회 · 망취소 · Recovery · 라우팅은 실연동에서도 그대로 쓰이는 수준으로 만든다.

## 2. 추후 확장 항목

### 2.1 오프라인 판매

- **v1에서는 지원하지 않는다.** POS_APP 서버 장애 시 판매가 멈추는 것을 알려진 한계로 둔다.
- 확장할 가치는 있다. 현업 POS의 핵심 기능이고, 구현하려면 클라이언트 로컬 저장 · 복구 후 업로드 · 중복 업로드 방지 · 재고 충돌 처리가 필요해 동기화 설계 역량을 보여줄 수 있다.
- 확장 시 범위 후보: 현금 판매만 오프라인 허용 (카드는 승인이 필요하므로 제외).
- **지금 설계에서 막지 말아야 할 것** (확장할 때 구조를 뒤집지 않기 위해)
  - 거래번호를 POS가 체번한다 (ADR-0002) — 서버 없이도 번호를 만들 수 있어야 함
  - 판매 저장 API는 거래번호 기준으로 멱등해야 한다 — 복구 후 같은 거래를 두 번 올려도 한 건
  - 재고 부족이어도 판매를 막지 않는다 (POS_APP 현재 정책) — 오프라인 판매가 나중에 들어와도 원장에 반영 가능

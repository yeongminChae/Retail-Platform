# 플랫폼 아키텍처

> 상태: **초안.** 확정된 것은 ADR 링크가 있는 항목뿐이다.

## 1. 시스템 구성

```text
[점포 — 점포마다]                                         [본사 — 하나]
POS 클라이언트 (마트 POS / 카페 키오스크*)
    │ HTTP — 얇은 클라이언트: 입력만 전달, 상태는 서버
    ▼
POS_APP 점포 서버 (판매 오케스트레이션) ── HTTP 승인 · 조회 · 취소 · 망취소 ──▶ Payment Server ── TCP ──▶ VAN Simulator
    │                                        ADR-0005                    (향후 VAN A/B · 카드사 직승인)
    │                                                                      │ posTrx별 결제 상태 (아웃박스, 5분, ADR-0025)
    │                                                                      ▼
    ├── 판매 확정 · 반품 · 마감 (아웃박스 + HTTPS, ADR-0014) ────────▶ ERP (기준정보 · 재고 원장 · 마감 · 대사)
    ◀── 자기 점포분 기준정보 (마감 후 일배치 전체 + 3분 폴링 긴급 변경, ADR-0034) ── ERP

※ 배치: ADR-0012 / ERP 통신은 점포 서버 백그라운드 작업만, 요청은 점포 → 본사: ADR-0013 / ERP는 받기만 함: ADR-0024
* 키오스크 배치는 미정 (설계 보류)
```

## 2. 데이터 소유권

| 데이터 | 소유 시스템 | 다른 시스템의 접근 | 상태 |
|---|---|---|---|
| 판매 · 판매 라인 | POS_APP | ERP는 읽기 / 이벤트 수신 | 결정 |
| 결제 거래 (승인 · 취소 · 망취소) | Payment Server | POS_APP은 결과만 저장 (승인번호 · BIN · 끝 4자리). ERP는 Payment가 보내온 posTrx별 결제 상태를 받음 | 결정 (ADR-0025) |
| 상품 마스터 · 가격 | ERP | POS_APP은 읽기 전용 사본, 판매 라인에 가격 · 과세 구분 스냅샷 | 결정 (ADR-0007) |
| 재고 | ERP (재고 원장) | POS_APP은 판매 확정 · 반품 전달만. 조회 · 쓰기는 ERP 화면에서만. 재고 부족이어도 판매 허용 | 결정 (ADR-0010) |
| 점포 · 기기 · 계산원 (계정 · 역할) | ERP (전 점포) | 각 점포 서버에 자기 점포분만 배포. 기기의 그날 운영 상태(개점 · 마감 · 거래번호 순번 · 시재)는 POS_APP 소유 | 결정 (ADR-0011) |
| 이상거래 | 발생 기록: POS_APP (`PAYMENT_ANOMALY`) / 처리 · 완료 기입: ERP | ERP가 Payment Server `MANUAL_REVIEW`와 함께 모아 수기 처리 | 결정 (ADR-0021) |

## 3. 공통 규칙

| 규칙 | 내용 | 상태 |
|---|---|---|
| 거래번호 · 거래 키 | POS_APP이 체번. 거래번호 4자리, 거래 키 = `점포-영업일-POS-거래번호` | 결정 (ADR-0002, 0045) |
| 결제 멱등 키 | `posTrx = 거래번호-결제순번` | 결정 (ADR-0002) |
| 영업일 | 점포 단위, 개점 · 마감 기준(자정 무관), 전환은 명시적 사건. 판매에 영업일 + 판매 확정 일시 저장. 24시간 점포는 v1 미지원 | 결정 (ADR-0018) |
| 금액 | 원 단위 정수, 판매가는 부가세 포함가, 부가세는 POS_APP이 판매 단위로 한 번 계산(원 미만 절사), 반품은 금액 · 부가세 · 수량 음수 | 결정 (ADR-0016) |
| 추적 ID | `X-REQUEST-ID`를 점포 서버가 생성해 Payment Server · ERP(아웃박스 경유)까지 전파, 로그 MDC. 거래번호(업무 키)와 구분. OpenTelemetry는 v1 제외 | 결정 (ADR-0017) |
| POS ↔ ERP 연계 | 판매 흐름은 ERP를 기다리지 않음. ERP 통신은 점포 서버의 백그라운드 작업으로만, 요청은 항상 점포 서버 → ERP. POS 클라이언트는 점포 서버하고만 통신 | 결정 (ADR-0013) |
| 요청 방향 | ERP는 다른 시스템을 호출하지 않음. 다른 시스템이 아웃박스로 ERP에 보내고 ERP는 멱등 수신 · 응답만 | 결정 (ADR-0024) |
| 데이터 접근 | 각 시스템은 자기 DB만 사용, 다른 시스템 데이터는 API로만 (읽기 포함). DB 계정 · 네트워크도 분리 | 결정 (ADR-0023) |
| 시스템 간 호출 타임아웃 | 호출하는 쪽의 타임아웃 > 호출받는 쪽의 하위 타임아웃 | 결정 (ADR-0003) |

## 3.1 마감 용어

| 이름 | 누가 | 단위 | 하는 일 | 근거 |
|---|---|---|---|---|
| POS 마감 | 계산원 · 매장 관리자 | POS 한 대 · 영업일 | 그 POS의 판매 종료, 시재 정산 | ADR-0019 |
| 점포 마감 | 매장 관리자 | 점포 · 영업일 | 전 POS 마감 확인 → 영업일 종료 → 일배치 계기 | ADR-0018, 0019 |
| ERP 일 대사 | ERP 배치 (자동) | 전 점포 · 영업일 | 다음 날 판매 수신 · 결제 대사 | ADR-0027 |
| 점포 월마감 | 매장 관리자 (ERP) | 점포 · 월 | 그 점포의 월 확정 | ADR-0033 |
| 전사 월마감 | 본사 (ERP) | 회사 · 월 | 회계 기간 확정, 재고 이월 | ADR-0033 |

## 5. POS_APP 모듈로 넘길 결정

카드 결제 연동 설계에서 함께 정했지만 POS_APP 안에서 끝나는 결정이다. POS_APP `docs/card-payment-integration-plan.md`로 옮긴다.

| # | 결정 |
|---|---|
| Q2 | 승인 대기 판매는 `SALES`의 `PENDING_PAYMENT` 상태 (TX1 저장 → 외부 호출 → TX2 확정) |

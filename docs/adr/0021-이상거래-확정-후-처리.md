# ADR-0021 되돌리기 실패는 매장에서 보상하지 않고 결과 확정 후 ERP에서 수기 처리한다

- 상태: 결정
- 날짜: 2026-11-19
- 관련 시스템: POS 클라이언트, POS_APP, Payment Server, ERP
- 대체: ADR-0004

## 맥락
- ADR-0004는 되돌리기(망취소 · 결제 포기 보상 취소 · 반품 카드 취소)가 3회 실패하면 이상거래로 저장하고 **매장에서 고객을 즉시 보상**하기로 했다.
- PAYMENT-SIMULATOR 확인 결과 (2026-11-18~19, `main`, `docs/DESIGN.md` · 코드):
  - 응답 없음은 실패가 아니라 결과 불명(`UNKNOWN_TIMEOUT`)으로 두고, 같은 요청을 다시 보내지 않는다.
  - Recovery가 결과 불명 · 오래 멈춘 거래를 VAN에 **조회만** 해서 확정한다 (재전송 없음). 확정하지 못하면 `MANUAL_REVIEW`로 넘긴다. 스케줄러는 기본 비활성이다.
  - `MANUAL_REVIEW` 목록 조회 API(`GET /api/admin/recovery/tasks?status=MANUAL_REVIEW`)와 재대기(requeue)는 있으나, 수기 확정 · 정산 기능은 없다.
  - 망취소가 성공해도 원승인 상태는 바뀌지 않으며, Recovery가 이후 원승인을 `APPROVED`로 확정할 수 있다 (VAN 조회 응답 내용은 미확인).
- 즉시 보상 후 Recovery가 "실제로는 돈이 빠지지 않았음 / 나중에 되돌려짐"을 확정하면 **이중 보상**이 생긴다. Payment Server의 원칙("확정 전에는 결과를 정하지 않는다")과도 어긋난다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| 매장 즉시 보상 (ADR-0004) | 고객이 그 자리에서 돈을 돌려받음 | 이중 보상 위험. 회수하려면 고객 연락 필요. 결과 확정 전에 매장이 결과를 단정 |
| 결과 확정 후 처리 | 이중 보상 없음. 돈이 빠진 경우 카드 취소로 돌려주므로 고객 연락 불필요. Payment 원칙과 일치 | 처리 전까지 고객 카드에 결제가 남아 있을 수 있음 |

## 결정
- **매장에서 즉시 보상하지 않는다.**
- 되돌리기를 최대 3회 시도해도 실패하거나 결과를 모르면, POS_APP은 그 건을 **이상거래(`PAYMENT_ANOMALY`, 상태: 확인 필요)**로 저장하고(원거래 · 결제 건 · 실패 사유 · 시도 횟수) 아웃박스(ADR-0014)로 ERP에 보낸다.
- 결과 확정은 Payment Server Recovery가 한다.
- **ERP가 처리 대상을 한곳에 모은다:** POS_APP 이상거래 + Payment Server `MANUAL_REVIEW` 목록.
- **처리는 수기로 한다.** 매장 관리자 또는 전산 담당자가 확정된 결과를 보고 처리한 뒤, ERP에 **완료 여부**(처리 결과 · 처리자 · 일시 · 사유)를 기입한다. 기입은 감사 로그를 남긴다. 자동 종결은 하지 않는다.
- **고객 안내:** 시스템 문구는 간략하게 둔다 (예: POS 화면 · 영수증에 "결제 확인 중" + 확인번호). 설명은 현업 방식대로 계산원이 구두로 전달한다.
- **자동 망취소는 유지한다** (ADR-0003 그대로). 결과 불명 승인은 계산대에서 조회 1회 후 바로 망취소해, 대부분 그 자리에서 정리한다. 이 ADR은 망취소까지 실패한 건만 다룬다. 계산원이 직접 망취소하는 기능은 두지 않는다.

## 대가와 후속 작업
- 처리 전까지 고객 카드에 결제가 남아 있을 수 있다. 처리 기한 · 고객 문의 대응 절차는 운영 절차로 둔다.
- 각 경우의 판매 처리(망취소 실패 시 그 카드 결제를 판매에서 어떻게 둘지, 반품 카드 취소 실패 시 반품을 완료할지)는 POS_APP 레포에서 정한다. 시스템 문구 · 확인번호 형식도 POS_APP에서 정한다.
- 수기 처리 수단(ERP 화면에서 Payment Server 취소를 호출할지, Payment 관리 기능 · VAN 문의로 할지)은 미정.
- ERP에서 완료를 기입했을 때 Payment Server `MANUAL_REVIEW`에도 수기 종결을 남길지는 미정 (Payment Server에 해당 기능 없음).
- 관리자가 판단할 근거로 posTrx별 최종 상태("고객 돈이 지금 빠져 있는가": 승인 · 취소 · 망취소 합산)가 필요하다. 이를 Payment Server 조회 API로 제공할지는 별도로 정한다. ERP 결제 대사에도 같은 기준이 필요하다.
- 플랫폼 실행 환경에서는 Payment Server Recovery 스케줄러를 켠다.

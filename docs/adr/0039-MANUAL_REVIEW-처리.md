# ADR-0039 MANUAL_REVIEW는 담당자가 VAN · 카드사에 확인하고 Payment에 운영 확정한 뒤 필요하면 운영 취소한다

- 상태: 결정
- 날짜: 2026-11-24
- 관련 시스템: Payment Server, ERP

## 맥락
- Payment Server Recovery가 VAN 조회로도 결과를 확정하지 못하면 `MANUAL_REVIEW`로 둔다. PAYMENT-SIMULATOR는 저장 · 로그 알림까지만 하고, 수기 확정(Force Resolve)은 미구현이다 (`docs/DESIGN.md` 알려진 한계).
- ERP는 Payment가 보낸 상태로 `MANUAL_REVIEW` 건을 목록에 모으고 처리 기록을 남긴다 (ADR-0025 · 0038). 처리 완료를 ERP에만 기록하면 Payment의 그 건은 계속 미확정으로 남아, ERP 일 대사가 매일 같은 건을 불일치로 다시 올린다 (자동 해소 조건이 충족되지 않음).
- 결과를 모르는 승인은 그대로는 취소할 수 없다. 취소는 확정된 승인에 하는 것이고, 망취소는 Payment가 원승인이 `UNKNOWN_TIMEOUT`일 때만 받는다 (코드 확인, ADR-0021 맥락). `MANUAL_REVIEW`는 VAN 조회가 계속 실패한 건이라 망취소도 같은 이유로 실패할 수 있다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| ERP에서만 처리 기록 · 대사 제외 | Payment 변경 없음 | Payment 원본 데이터가 계속 틀림. 상태 전송 · 매입에 영향 |
| Payment에 운영 확정 추가 | 원본이 맞아짐 → 상태 전송 · 대사 · 매입이 모두 맞음. Force Resolve 한계 해소 | Payment 기능 추가 |

## 결정
- **사실 확인은 업무다.** 전산 담당자가 **VAN · 카드사에 전화 · 메일로 확인**한다.
- **확인한 결과는 Payment Server에 운영 확정한다.** 전산 담당자 1인이 Payment 운영 기능으로 그 거래를 확인된 결과(승인됨 / 거절됨 등)로 확정한다. 확인 근거(문의처 · 일시 · 담당자) · 사유를 감사 로그에 남긴다 (ADR-0036 운영 권한).
- **확정 이후 흐름은 기존 경로를 그대로 쓴다.**
  1. 운영 확정 → Payment 상태 변경 → 아웃박스 → 5분 전송으로 ERP 반영 (ADR-0025). 새 통신 경로 · 웹소켓은 필요 없다.
  2. 확정 결과가 "승인됨"이고 어떤 확정 판매에도 쓰이지 않았으면 → 운영 취소로 반환 (ADR-0038).
  3. ERP 대사에서 그 건의 불일치가 해소된다.
- **ERP 반환 대상 조회(ADR-0038)는 조회 시점의 최신 데이터로 판단한다.** 다음 날 대사 배치를 기다리지 않아, 운영 확정 직후(상태 전송 반영 후) 운영 취소를 실행할 수 있다.

```text
MANUAL_REVIEW → 담당자 VAN · 카드사 확인 (전화 · 메일)
             → Payment 운영 확정 (승인됨 / 거절됨)
             → 5분 전송으로 ERP 반영
             → 승인됨 + 판매에 안 쓰임이면 운영 취소 (Payment가 ERP에 반환 대상 확인)
```

## 대가와 후속 작업
- PAYMENT-SIMULATOR 과제: 운영 확정 기능 (확정 가능한 상태 · 결과 범위, 이미 terminal인 건의 충돌 처리, 감사).
- 문의 절차 · 연락처 · 기한은 운영 절차로 둔다.

# 나중에 설계할 것

1단계 설계 중 "지금은 미루기로 한" 항목을 모아 둔다. 정해지면 ADR(시스템 간) 또는 해당 레포 `docs/`(한 시스템 안)로 옮기고 여기서 지운다.

## 시스템 간 (이 레포에서 결정)

| 항목 | 내용 | 관련 | 언제 |
|---|---|---|---|
| 서버 재기동 시 미완료 판매 (Retail-POS Q9 재검토) | Payment Server는 따로 돌아 승인 기록이 안전하므로 자동 취소는 불필요. 미완료 판매를 이어서 진행할지, 손님이 떠난 경우 처리 | ADR-0021, architecture.md 5장 Q9 | 장바구니 저장소(Redis 도입 여부)와 함께 |
| **부분 반품 (상용화 확장 1순위)** | v1은 전체 반품 + 원거래 연결 재판매로 대신함(ADR-0032). 고객 카드에 전액 취소 + 새 결제가 함께 찍히고 할부가 다시 잡히는 약점. Payment 부분 취소는 PAYMENT-SIMULATOR `docs/phase2/08-부분-취소.md`에서 설계(여러 번, 남은 금액 예약). 남은 것: 라인별 부가세 · 복합결제 환불 순서 · POS 화면, 그리고 **취소 재시도는 같은 취소 posTrx로**(승인 재결제와 반대) 규칙을 ADR로 | ADR-0016, 0032, Retail-POS Q5 | v1 이후 첫 확장 |
| 정산 입금 데이터 · 재매입 | 매입은 ADR-0049로 결정. 남은 것: 카드사 입금 데이터를 ERP에 넣는 경로, 반송 건 재매입 절차, 수수료율 기준(실제 계약 구조 미확인) | ADR-0049 | ERP 정산 설계 때 |
| 할인 · 행사가 · POS 매가 변경 | v1 범위 밖. 매가 변경은 할인의 한 형태로 함께 설계 | ADR-0007, 0036 | 할인 설계 때 |
| 전산 담당자 운영 DB 작업 절차 | 조회 · 데이터 정정의 승인 · 기록 방식 | ADR-0036 | 운영 설계 때 |
| 망취소 거절 시 POS 규칙 | Recovery가 원승인을 먼저 확정하면 망취소가 거절됨 → 재조회 후 승인이면 취소로 전환 | ADR-0003, ADR-0021 | Q9와 함께 |

## 카페 키오스크 설계 때 다시 볼 것

1단계 플랫폼 규칙(얇은 클라이언트 · 결제 연동 · 거래번호 · 금액 · 아웃박스 · 기준정보 배포 · 영업일 · 대사)은 키오스크에도 그대로 쓴다. 아래는 마트 POS 전제(사람이 있는 계산대 · 같은 사업자)에 기대고 있어 키오스크에서 다시 정해야 하는 것이다.

| 항목 | 마트 POS 전제 | 키오스크에서 걸리는 점 | 관련 |
|---|---|---|---|
| 사업자 · 매출 귀속 | 점포 = 사업자 하나 | 카페가 다른 사업자일 수 있음 → 매출 귀속 · 정산 · 대사 · 월마감을 사업자별로 나눠야 함 | standards.md, ADR-0027 · 0033 |
| 배치 | 점포 서버 (매장 안) | 카페 · 소상공인 매장은 점포 서버를 둘 수 없음 → **두 방식 검토:** 점포 설치형(마트, 지금 설계) / 중앙 호스팅형(본사 · 클라우드의 같은 Retail-POS 서버가 여러 점포를 맡음). 코드는 하나, 배치 위치만 다르게. 중앙형은 인터넷 장애 시 판매 중단 · 기기 인증 · 점포별 데이터 격리 · 사업자 분리가 필요. 전부 중앙형(마트 인터넷 장애 위험) · 단말 내장 서버(체번 · 마감 · 아웃박스가 단말마다)는 제외 방향 | ADR-0012, standards.md 2장 |
| 로그인 · 계정 | 계산원 사번 + PIN | 무인이라 계산원 로그인이 없음 → 단말 인증 | ADR-0011 · 0029 |
| 시재 · 마감 | 계산원 시재 | 현금이 없으면 시재 없음. 마감 주체(누가 마감하나) | ADR-0019 |
| 결제 불명 안내 | 계산원이 구두로 설명 | 설명할 사람이 없음 → 화면 안내 · 확인번호 출력, 고객이 바로 떠남 | ADR-0021 |
| 반품 | 고객센터 POS | 키오스크에서 반품 불가 → 카페 카운터의 어느 기기가 처리하나 | ADR-0031 |
| 단말 인증 | 점포 내부망 + 계산원 로그인이라 단말 인증서 없음 | 본사(중앙)에 직접 붙으면 인터넷 · LTE라 IP 차단이 안 됨(IP는 바뀌고 신원이 아님) → 기기 인증(등록 코드 → 단말 키, 또는 mTLS) 필요. IP를 앱 DB로 관리하지 않음 | ADR-0012, 0044 |
| 품절 | — | 판매 가능 여부 표시 | ADR-0013 |
| 주문 흐름 | 장바구니 → 결제 | 옵션 · 대기번호 · 주방 출력 (Retail-POS 안) | — |

## Retail-POS 안 (Retail-POS 레포 `docs/`로 옮길 것)

Retail-POS 정리 중 발견 (2026-11-20, Retail-POS `main` `fc282eb` 기준).

### 장바구니 저장소 · 동시성
- 장바구니는 인메모리. 같은 거래 키에 동시 요청이 오면 수량 변경 · 취소가 원자적이지 않음 (서로 다른 거래끼리는 안전 — `ConcurrentPosIntegrationTest`).
- 현재 전제: "한 거래는 한 단말(POS/키오스크)이 다룬다" — 코드 주석에 기록됨.
- 장바구니를 Redis · DB로 옮기거나 서버를 여러 대로 늘릴 때 동시성 정책과 함께 결정. 재기동 시 장바구니 유실 여부가 Q9와 연결됨.

### 미사용 코드 정리 (refactor)
- `domain/model/product/Product.java` — 클래스 전체 미사용 (상품 조회는 `ProductQueryDto`). 상품/메뉴 모델 설계 시 재사용 또는 삭제 결정 (ADR-0007: 상품은 ERP 사본).
- `Cart.getCartLineQty()` — 호출처 없음.
- `Payment`의 편의 메서드 `paymentId()` · `posNo()` · `tranNo()` · `requestedAt()` — 호출처 없음 (JSON 직렬화 대상 아님).

### 스키마 주석 불일치
- `schema.sql`의 `SALES.APPROVED_AT` · `RECEIPT_JOURNAL.APPROVED_AT` 주석은 "ISO8601"이지만 실제 저장 형식은 `yyyy-MM-dd HH:mm:ss` (Asia/Seoul).
- 운영 DB에서 추출한 파일이라 운영 스키마 주석부터 고쳐야 함 → 스키마 정리 시 Retail-POS `docs/schema-issues.md`와 함께.

### 문서 정정
- Retail-POS CLAUDE.md "미완성 부분"의 "`ProductController`의 엔드포인트는 주석 처리됨" → 실제로는 경로(`/api/products`)만 있고 엔드포인트 없음. 상품/메뉴 API 추가 시 갱신.

### 기존 보류 항목 (Retail-POS `docs/bugfix-plan.md` · `api-change-plan.md`)
- B12c 성인 인증, B14b 계산원(현재 "테스터" 고정 → ADR-0011), B12d 재고 부족 차단(정책상 허용 → ADR-0010), B17 enum ↔ DB CHECK 불일치, T2 조회 트랜잭션, L5 결제 수단별 저장 정책(카드).

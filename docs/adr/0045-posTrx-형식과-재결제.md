# ADR-0045 번호 용어와 posTrx 자릿수를 고정하고, 망취소 뒤 재결제는 다음 결제순번으로 한다

- 상태: 결정
- 날짜: 2026-11-26
- 관련 시스템: POS_APP, Payment Server, ERP
- 관련: ADR-0002 (보완), ADR-0025 (맥락 정정)

## 맥락
- ADR-0002는 posTrx = `거래번호-결제순번`으로만 정했고, 자릿수는 정하지 않았다.
- 이전 ADR들은 "거래번호"를 `점포-영업일-POS-순번` 전체로 썼다. POS_APP 코드는 거래번호(`tranNo`)를 **마지막 4자리**로 쓰고, 거래를 `점포 + POS + tranNo`로 찾는다. 용어가 둘로 갈려 있다.
- PAYMENT-SIMULATOR 확인 (2026-11-25, `main` `2e05320`):
  - Payment Server 승인 DTO와 VAN Simulator는 posTrx를 `^\d{4}-\d{8}-\d{4}-\d{4}$`로 검증한다. 결제순번이 붙은 형식은 거부된다.
  - 같은 posTrx의 새 승인 시도(`attemptSeq` +1)는 직전 시도가 `DECLINED`일 때만 허용한다. `UNKNOWN_TIMEOUT`(망취소 후 포함)이면 같은 내용은 저장된 결과를 다시 돌려주고, 다른 내용은 `POS_TRX_ALREADY_USED`로 거부한다.
- ADR-0025 맥락은 "결과 불명 → 망취소 → **같은 posTrx로 재결제**"를 예로 들었지만, 위 동작 때문에 현재 코드에서는 그렇게 할 수 없다.
- 대사 · 정산에서 번호를 보려면 번호가 애매하게 건너뛰는 일이 없어야 한다.

## 선택지
| 항목 | 선택지 | 장점 | 단점 |
|---|---|---|---|
| 형식 검증 | 자릿수 고정 | 잘못된 번호를 입구에서 막음. Payment · VAN 형식 검증을 그대로 씀 | POS_APP이 형식을 바꾸면 Payment · VAN도 바꿔야 함 |
| | 문자 집합 · 길이만 | 형식 변경에 영향 없음 | 잘못된 번호가 들어와 대사에서야 발견 |
| posTrx 전달 | 문자열 하나 | Payment · VAN 현행 그대로. Payment는 POS 번호 체계를 몰라도 됨 (ADR-0025 범용) | 뜻이 문자열에 묻힘 |
| | 필드로 나눔 | 뜻이 잘 보임 | Payment · VAN · ERP 계약과 키 전부 변경 |
| 망취소 뒤 재결제 | 같은 posTrx | posTrx 하나 = 고객이 의도한 결제 하나 | 결과를 모르는 시도 위에 같은 키로 새 시도. Payment 멱등 판단 변경 필요 |
| | 다음 결제순번 | Payment 변경 없음. 확실한 실패(`DECLINED`) 뒤에만 같은 키 재사용 | 한 거래에 망취소된 posTrx가 남음 |

## 결정
- **번호 용어** (이 ADR부터. 이전 ADR의 "거래번호"는 아래 "거래 키"를 뜻한다):

| 이름 | 형식 | 예 | 쓰는 곳 |
|---|---|---|---|
| 거래번호 | 4자리, POS별 거래 순서 | `0199` | POS_APP |
| 거래 키 | 점포(4)-영업일(8)-POS(4)-거래번호(4) | `1000-20261126-0001-0199` | POS_APP 판매 유니크 키 (ADR-0044), ERP |
| 영수증번호 | 점포(4)-발행일(8)-POS(4)-거래번호(4) | `1000-20261126-0001-0199` | 영수증 출력 · 고객 문의 (ADR-0046) |
| 결제순번 | 2자리, 한 거래 안의 카드 결제 건 | `01` | posTrx 끝 |
| **posTrx** (결제 건 번호) | 거래 키-결제순번 (4-8-4-4-2) | `1000-20261126-0001-0199-01` | POS_APP ↔ Payment, Payment → ERP |
| attemptSeq | 같은 posTrx 안의 승인 시도 순번 | `1`, `2` | Payment가 매김 |

- **posTrx가 필요한 이유:** 한 거래에 카드 결제가 여러 건일 수 있고(복합결제 · 재결제), 응답이 사라져도 POS가 같은 결제 건을 조회 · 망취소로 가리켜야 하므로(ADR-0003) **번호를 POS가 먼저 정해 보낸다**. 같은 posTrx로 다시 보내도 결제가 두 번 되지 않는다 (멱등).
- **posTrx는 문자열 하나**로 보내고, Payment Server와 VAN Simulator는 위 형식을 입구에서 검증한다. 영업일은 실제 날짜, 결제순번은 `01`~`99`. 형식을 바꿀 때는 새 ADR로 바꾼다.
- **거래번호는 결과가 확실할 때만 증가한다:** 거래 완료 · 거래 중지 · 보류 · 개점 / 마감처럼 그 거래의 상태가 확정되는 시점이다. 결제 재시도 때문에 거래번호가 바뀌지 않는다 (POS_APP 규칙, 세부는 POS_APP 레포).
- **재결제:**
  - 직전 시도가 `DECLINED`(확실한 실패)면 **같은 posTrx**로 다시 승인한다 (Payment가 attemptSeq를 올림).
  - 결과 불명 → 조회 → 망취소(ADR-0003) 뒤에는 **같은 거래의 다음 결제순번**(새 posTrx)으로 다시 결제한다.
- **결제 상태 전송(ADR-0025)은 posTrx별 그대로다.** 망취소된 posTrx는 "안 빠짐"(망취소 실패면 "빠짐"/"미확정")으로 따로 나간다. 판매에 쓰이지 않은 승인은 ERP 대사가 찾는다 (ADR-0027). ADR-0025의 "같은 posTrx 안 빠진 승인 2건 이상 = 이중 결제"는 `DECLINED` 뒤 재시도 경우에 해당한다.
- Payment Server의 posTrx 발급 API(`/pos-trx/issue` · `/eot`)는 제거한다 (ADR-0002 후속).

## 대가와 후속 작업
- 한 거래에 posTrx가 여러 개 생길 수 있다. ERP 화면 · 대사는 거래 키로 묶어 보여 줘야 한다 (ERP 레포).
- 결제순번 상한 99는 한 거래의 결제 건으로 충분하다고 본다 (가정).
- 보류 거래의 번호 처리(보류 해제 시 같은 거래번호를 이어 쓰는지)는 POS_APP 레포에서 정한다.
- PAYMENT-SIMULATOR 상세: `docs/phase2/01-posTrx-형식.md`.

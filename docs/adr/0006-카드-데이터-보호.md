# ADR-0006 카드 데이터 보호는 두 단계로 적용한다

- 상태: 결정
- 날짜: 2026-11-18
- 관련 시스템: POS 클라이언트, POS_APP, Payment Server

## 맥락
- 표현 원칙: "PCI DSS 준수"는 심사가 필요한 표현이라 쓰지 않는다. **"PCI DSS 원칙을 참고한 카드 데이터 보호 설계"**로 쓴다.
- Payment Server는 이미 카드번호 원문 저장 금지, BIN 8자리 · 끝 4자리 · 마스킹 번호 저장, HMAC-SHA256 fingerprint, 로그 마스킹을 갖췄다. BIN은 카드사 판별(`BIN_CATALOG`)과 향후 라우팅에 쓴다.
- POS_APP은 `RECEIPT_JOURNAL`에 `Sale` 전체를 JSON으로 직렬화해 저장하므로, 카드 결제가 붙으면 카드번호가 새어 들어갈 위험이 있다.
- 국내 오프라인 가맹점은 보안인증 IC 단말기가 카드번호를 읽는 시점에 암호화해 VAN으로 보내는 구조다 (2015년 여신전문금융업법 개정 이후 IC 단말기 의무화, 여신금융협회 보안인증).

## 결정
- **1단계 (첫 연동):** 카드번호는 POS_APP을 통과만 한다. 다음을 테스트로 증명한다.
  - 카드 결제 후 POS_APP의 모든 테이블(`RECEIPT_JOURNAL` 포함)과 로그에 카드번호 원문이 없다
  - 오류 응답(`ProblemDetail.detail`)과 요청 로그에 카드번호가 나가지 않는다
- **2단계 (단말 암호화):** 카드 리더 시뮬레이터가 카드번호를 읽자마자 Payment Server 공개키로 암호화한다. POS_APP은 **암호문 + BIN**만 받아 중계하고 복호화 키가 없다. Payment Server가 복호화 → 라우팅 → 승인한다.

| 시스템 | 카드번호 | 보안 범위 |
|---|---|---|
| 카드 리더 (시뮬레이터) | 읽자마자 암호화 | 포함 |
| POS_APP | 암호문 + BIN, 키 없음 | 제외 (목표) |
| Payment Server | 복호화 · 라우팅 · 전문 생성 | 포함 |

## 대가와 후속 작업
- 2단계는 Payment Server 승인 API 변경이 필요하다. 키 관리는 처음엔 설정 파일 키 쌍으로 두고 한계로 명시한다.
- 실제 단말이 BIN을 평문으로 함께 넘기는지는 VAN마다 다를 수 있다 (가정). 결제 SDK 분석에서 확인한다.
- 멀티 VAN · 카드사 직승인 라우팅은 Payment Server 확장 과업으로 둔다.

# 상용화 기준

> 상태: **1차 결정 완료 (2026-11-18).** 남은 것: 개인정보 범위 확인, 키오스크 설계, 이상거래 심화.
> 이 문서가 모든 설계의 판단 기준이다. "다 됐나?"는 여기 체크리스트와 `e2e/` 시나리오 통과 여부로 판단한다.

## 0. 카드 결제 모듈이 시뮬레이터인 것에 대해

결제 쪽 상용화 수준은 **"VAN 어댑터만 교체하면 실연동이 되는 구조"**로 정의한다.

- 실제 VAN · 카드사 전문 송수신은 시뮬레이터로 대체한다 (Payment Server의 `VanGateway` 경계).
- 그 위의 거래 상태 관리 · 멱등성 · 조회 · 망취소 · Recovery · 라우팅은 실연동에서도 그대로 쓰이는 수준으로 만든다.

## 1. 체크리스트

| 구분 | 항목 | 왜 필요한가 | 포함 여부 |
|---|---|---|---|
| 판매 | 마트 POS 판매 · 현금/카드 복합결제 · 전체 반품 | 기본 업무 | 포함 |
| 판매 | 카페 키오스크 (옵션 · 대기번호 · AI 음성 주문) | 같은 API로 다른 채널 지원 | **설계 보류** — 마트와 관리 주체(사업자)가 다를 수 있어 사업자 · 매출 귀속 · 정산 분리를 함께 설계해야 함 |
| 법·세무 | 과세/면세 구분 | 면세 상품이 섞이면 영수증 · 매출 집계가 달라짐 | **v1 포함** — 상품 마스터에 과세 구분, 판매 라인에 스냅샷, 집계는 과세 · 면세 · 부가세 분리 |
| 법·세무 | 현금영수증 | 현금 결제에 필요 | **추후 확장** — Payment Server 승인 유형 추가로 붙일 수 있음 |
| 운영 | POS 일마감 · 계산원 시재 정산 | 매장 운영의 기본 단위. 영업일 정의(ADR-0002 후속)와 ERP 월마감 집계 기준 | **v1 포함** — 계산원 마스터 포함 (POS_APP의 `"테스터"` 고정 해소) |
| 운영 | 권한 · 감사 로그 | 반품 · 가격 변경 · 이상거래 처리 주체 추적 | **v1 포함** — 역할 3개(계산원 / 매장 관리자 / 본사), 민감 작업(반품 · 가격 변경 · 이상거래 처리 · 마감)만 감사 로그. 반품은 관리자 승인 필요 |
| 운영 | 이상거래 처리 화면 · 대사 | ADR-0004의 이상거래를 누가 어떻게 닫는가. Payment Server Recovery가 나중에 같은 거래를 확정하면 매장 보상과 이중 · 누락이 생길 수 있음 | **v1 포함, 1차 설계 후 심화** — Payment Simulator의 Recovery · Inquiry와 비교 분석하며 설계 |
| 장애 | 오프라인 판매 | 서버 · 네트워크 장애 시 판매 지속 여부 (얇은 클라이언트 구조와 충돌) | **v1 미지원, 추후 확장** (3장) |
| 장애 | 시스템별 다운 시 동작 | Payment · ERP가 죽었을 때 POS는 어떻게 하나 | 일부 결정 (ADR-0003) |
| 장애 | 백업 · 모니터링 · 알림 | Recovery 실패 · MANUAL_REVIEW · 이상거래를 누가 언제 아는가 | **v1 포함** — Actuator · Prometheus · Grafana 지표(승인 성공률 · UNKNOWN 건수 · 미종결 이상거래 · 마감 상태), 임계치 알림 1채널(예: Slack 웹훅), 추적 ID 전 시스템 전파, DB 정기 백업 + 복구 리허설 1회 |
| 보안 | 카드 데이터 보호 | PCI DSS 원칙 참고 (준수 주장 아님) | 결정 (ADR-0006) |
| 보안 | 개인정보 (회원 · 현금영수증 식별번호 등) | | v1 범위는 계산원 정보뿐 (회원 없음, 현금영수증은 확장) — 확인 필요 |
| 성능 | 피크 시간 동시 POS 대수 · 응답 목표 | DB · Redis 설계 검증 기준 | **v1 포함** — 2장 |
| ERP | 기준정보 · 구매 · 입고 · 재고 원장 · 월마감 · 대사 | 판매가 재고 · 정산까지 이어짐 | 포함 (모듈별 깊이 미정) |

## 2. 성능 목표

숫자는 **가정치**다. 부하 테스트(k6 등)로 검증하고, 결과에 따라 목표를 조정할 때는 이 문서에 기록한다.

| 단계 | 규모 | 역할 | 기준 |
|---|---|---|---|
| 1 | 대형점 1개, POS 30대 동시 피크 | **v1 합격 기준** | 장바구니 · 결제 API 응답 p95 목표 통과 (구체 수치 미정) |
| 2 | 다점포 (점포 수십 개) | 설계 기준 | 점포 코드를 모든 키 · 인덱스에 포함하는 등 확장을 막지 않기. 성능은 측정만 |
| 3 | 장애 상황 (VAN 응답 지연 · 유실) | **v1 합격 기준** | 한 POS의 결제가 VAN 지연에 묶여 있어도 다른 POS의 결제 응답 시간이 목표 안에 있음 |

## 3. 추후 확장 항목

### 3.1 오프라인 판매

- **v1에서는 지원하지 않는다.** POS_APP 점포 서버 장애 시 판매가 멈추는 것을 알려진 한계로 둔다.
- 범위: 오프라인 판매는 **점포 서버까지 장애인 경우**(POS 클라이언트가 서버 없이 판매)를 말한다. 본사 회선만 끊긴 경우는 점포 서버가 판매를 계속하므로 오프라인 판매가 아니다 (ADR-0012).
- 확장할 가치는 있다. 현업 POS의 핵심 기능이고, 구현하려면 클라이언트 로컬 저장 · 복구 후 업로드 · 중복 업로드 방지 · 재고 충돌 처리가 필요해 동기화 설계 역량을 보여줄 수 있다.
- 확장 시 범위 후보: 현금 판매만 오프라인 허용 (카드는 승인이 필요하므로 제외).
- **지금 설계에서 막지 말아야 할 것** (확장할 때 구조를 뒤집지 않기 위해)
  - 거래번호를 POS가 체번한다 (ADR-0002) — 서버 없이도 번호를 만들 수 있어야 함
  - 판매 저장 API는 거래번호 기준으로 멱등해야 한다 — 복구 후 같은 거래를 두 번 올려도 한 건
  - 재고 부족이어도 판매를 막지 않는다 (POS_APP 현재 정책) — 오프라인 판매가 나중에 들어와도 원장에 반영 가능

### 3.2 24시간 점포

- **v1에서는 지원하지 않는다.** 영업일은 점포 마감 → 다음 영업일 개시로 전환한다 (ADR-0018).
- 확장 시 필요한 것: 판매 중 영업일 전환(결제 중 판매 · 미마감 계산원의 귀속), 판매 중 기준정보 교체(ADR-0015의 "마감 후 · 개점 전" 일배치 전제 대체).
- **지금 설계에서 막지 말아야 할 것:** 영업일 전환을 시각이나 "판매 없는 시간대"가 아니라 명시적 사건으로 둔다.

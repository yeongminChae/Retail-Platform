# ADR-0025 Payment Server는 posTrx별 결제 상태를 아웃박스로 모아 5분마다 ERP에 보낸다

- 상태: 결정
- 날짜: 2026-11-20
- 관련 시스템: Payment Server, ERP

## 맥락
- ERP는 두 가지 일에 결제 상태가 필요하다.
  - 이상거래 화면: 관리자가 "카드 취소 필요 / 조치 불필요"를 판단 (ADR-0021, 0022)
  - 결제 대사: 판매 금액 = 실제 결제된 금액 (standards.md)
- Payment Server는 망취소가 성공해도 원승인 상태를 바꾸지 않고, Recovery가 그 원승인을 이후 `APPROVED`로 확정할 수 있다 (ADR-0021 맥락). 승인 상태만 보면 결제 여부를 잘못 판단한다.
- 한 posTrx(`거래번호-결제순번`, ADR-0002) 안에 시도가 여러 번 있을 수 있다 (예: 결과 불명 → 망취소 → 같은 posTrx로 재결제).
- 플랫폼 정책상 취소를 다시 취소하는 거래와 부분 취소는 없다 (전체 반품만).
- ERP는 다른 시스템을 호출하지 않는다 (ADR-0024).

## 선택지
| 항목 | 선택지 | 장점 | 단점 |
|---|---|---|---|
| 전달 방식 | Payment가 아웃박스로 주기 전송 | ADR-0024와 일치. 점포 서버와 같은 패턴 | 실시간 아님 |
| | ERP가 Payment API 조회 | 실시간 | ADR-0024 위반 |
| 전송 단위 | posTrx별 합산 상태 | 이중 결제를 발견할 수 있음. 승인 · 취소 · 망취소 해석을 Payment가 책임 | Payment에 합산 로직 필요 |
| | 승인 · 취소 · 망취소 원장 그대로 | Payment 변경 적음 | ERP가 Payment 내부 규칙을 다시 구현 |
| 주기 | 1분 | 빠름 | 이 용도에는 불필요하게 잦음 |
| | 5분 | 관리자 수기 처리 · 마감 후 대사에 충분 | 최대 5분 지연 |

## 결정
- **결제 상태 판단 기준 ("고객 돈이 지금 빠져 있는가"):** 승인이 `APPROVED`이고 그 승인에 대해 성공한 취소 · 망취소가 없으면 **빠짐**. 결과가 확정되지 않은 승인 · 취소 · 망취소가 남아 있으면 **미확정**. 그 밖에는 **안 빠짐**.
- **전송 단위는 posTrx**다. 그 posTrx의 모든 시도를 합쳐 다음을 보낸다.
  - 상태: 빠짐 / 안 빠짐 / 미확정
  - 빠진 금액, 빠진 승인 목록 (승인번호 · 시도 순번) — 빠진 승인이 2건 이상이면 고객 이중 결제다
  - 미확정 건, `MANUAL_REVIEW` 여부
  - 버전 (posTrx별 변경 순번)
- **보내는 시점:** posTrx의 상태가 바뀔 때(승인 확정 · 취소 · 망취소 · Recovery 확정 · `MANUAL_REVIEW` 전환) 같은 트랜잭션으로 Payment Server 아웃박스에 기록한다.
- **보내는 주기:** 스케줄러가 **5분마다** 아웃박스를 ERP로 보낸다 (HTTPS). 주기는 설정값이며 기본 5분이다.
- **ERP 수신:** posTrx 기준 멱등으로 받는다. 받은 버전보다 낮은 버전은 무시한다. 이상거래 화면과 결제 대사는 이 데이터를 쓴다.
- **범용 기능으로 만든다.** Payment Server에는 "ERP 전용"이 아니라 "결제 상태 전송" 기능으로 두고, 받는 곳은 설정으로 정한다. PAYMENT-SIMULATOR가 독립 프로젝트로 남도록 하기 위해서다.

## 대가와 후속 작업
- ERP 화면의 결제 상태는 최대 5분 늦다. `MANUAL_REVIEW` 알림은 모니터링 지표로 나가므로 이 지연과 무관하다.
- ERP 일 대사는 점포 마감 후 마지막 전송을 기다린 뒤 판정한다. 대기 기준은 대사 설계에서 정한다 (ADR-0019 후속과 함께).
- Payment Server 구현 과제: 합산 상태 계산, 아웃박스 · 스케줄러 전송, 전송 대상 설정. Recovery 스케줄러 활성화도 함께 한다 (ADR-0021).
- 계약(OpenAPI)은 `contracts/`에 둔다.

# ADR-0016 금액은 원 단위 정수로 다루고 부가세는 POS_APP이 판매 단위로 한 번 계산한다

- 상태: 결정
- 날짜: 2026-11-18
- 관련 시스템: POS_APP, Payment Server, ERP

## 맥락
- 판매 금액 · 부가세가 POS_APP → ERP로 넘어가고, ERP는 판매 = 결제 = 원장 대사를 한다 (standards.md). 시스템마다 계산 · 반올림이 다르면 대사가 1원 단위로 깨진다.
- v1에 과세/면세 구분이 들어간다. 판매 라인에 판매가 · 과세 구분을 스냅샷한다 (ADR-0007).
- 반품은 원거래를 `REFUNDED`로 두고 반품 판매를 새로 저장한다 (POS_APP 결정 Q4). 전체 반품만 지원한다 (Q5).

## 선택지
**부가세 계산 단위**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 판매(영수증) 단위로 한 번 | 절사 오차가 한 번만 생김. 영수증 합계와 일치 | 라인별 부가세가 필요하면 배분 규칙이 따로 필요 |
| 라인 단위 | 라인별 값이 바로 있음 | 라인 수만큼 절사 오차가 쌓여 합계와 어긋남 |

**반품 금액 표현**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 양수 + 거래 유형 | 금액 검증 단순 | 집계 때 유형을 보고 빼야 함 |
| 음수 금액 | 더하기만 하면 집계됨 | 모든 시스템이 같은 부호 규칙을 지켜야 함 |

## 결정
- **타입:** 금액은 **원 단위 정수**다 (Java `long`, DB `BIGINT`, JSON 정수). 실수 타입은 쓰지 않는다. 통화는 KRW만 다루며 통화 코드는 두지 않는다.
- **판매가:** 상품 마스터와 판매 라인의 판매가는 **부가세 포함가**다.
- **부가세 계산:** 판매 한 건 단위로 한 번 계산한다.
  - `부가세 = 과세 상품 합계 ÷ 11, 원 미만 절사`
  - `공급가액 = 과세 상품 합계 − 부가세`
  - 면세 상품 합계는 따로 둔다. 판매에는 과세 합계 · 공급가액 · 부가세 · 면세 합계를 저장한다.
- **계산 주체:** POS_APP이 한 번 계산해 판매에 저장한다. ERP는 다시 계산하지 않고 받은 값을 쓴다.
- **반품:** 반품 판매의 **금액 · 부가세 · 수량은 음수**로 표현한다. 값은 원거래에 저장된 값의 부호만 바꾼 것이며 다시 계산하지 않는다. ERP는 판매와 반품을 더하기만 해서 집계한다.
  - 이 부호 규칙은 판매 데이터(POS_APP 판매 · ERP 전송, ADR-0014)에 적용한다. Payment Server 취소 API의 금액 표현은 Payment Server 계약을 따른다.

### 사실과 가정
- **사실:** 부가세율은 10%다.
- **근거 자료 있음 (법령 원문 미확인):** 대가에 부가세가 포함됐는지 분명하지 않으면 받은 금액의 110분의 100을 공급가액으로 본다는 규정(부가가치세법 제29조 제7항)이 실무 자료에 인용된다.
- **가정:** 부가세의 원 미만 절사와 영수증 단위 계산은 실무 관행으로 본다. 확인한 실무 자료들도 절사 단위(원 미만 / 10원 미만)가 서로 달랐고, 법령에 절사 규정이 없다는 주장도 있었다.

## 대가와 후속 작업
- 상용화 판단 전에 부가세 계산 · 절사 방식을 세무 전문가나 국세청 안내로 확인한다. 계산이 POS_APP 한 곳에 있으므로 바뀌어도 고칠 곳은 하나다.
- 라인별 부가세가 필요해지면(예: 부분 반품 확장) 판매 단위 부가세를 라인에 배분하는 규칙을 새로 정한다.
- 할인 · 행사가의 금액 규칙은 미정 (v1 범위 밖, ADR-0007 후속).

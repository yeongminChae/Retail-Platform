# 1단계 플랫폼 설계 요약

> 기준일: 2026-11-24 (1단계 1차 완료). **지금 유효한 결정만** 모았다. 근거와 바뀐 이력은 각 ADR에 있다. 대체된 ADR(0004 · 0008 · 0009 · 0015 · 0020 · 0022 · 0028 · 0030 · 0037 · 0038 · 0039)은 여기서 다루지 않는다.

## 1. 한 장 그림

```text
[점포 — 점포마다]                                   [본사 — 하나]

POS 클라이언트 (판매 POS · 고객센터 POS)
   │  얇은 클라이언트: 입력만, 상태는 서버
   ▼
POS_APP 점포 서버 ──── 승인 · 조회 · 취소 · 망취소 (동기) ────▶ Payment Server ── TCP ──▶ VAN
   │                                                              │
   ├── 판매 · 반품 · 마감 요약 (아웃박스, 수시) ───────▶ ERP ◀──┘ posTrx별 결제 상태 (아웃박스, 5분)
   ├── 기준정보 요청: 마감 후 일배치 전체 ────────────▶ ERP
   └── 긴급 변경 4종 요청: 3분 폴링 (생존 신호 겸용) ─▶ ERP
                                                    Payment ── 운영 요청 가져오기 (5분) ─▶ ERP
                                                    ERP는 응답만, 먼저 호출하지 않음
```

## 2. 원칙 6개

| # | 원칙 | ADR |
|---|---|---|
| 1 | **POS는 판매만.** 기준정보 · 재고 · 쓰기 작업은 ERP 화면에서 | 0013 |
| 2 | **요청은 안쪽에서 바깥쪽으로.** 클라이언트 → 점포 서버 → 본사. ERP는 받기만 | 0013, 0024 |
| 3 | **판매 흐름은 ERP를 기다리지 않는다.** ERP 통신은 백그라운드 작업 | 0013 |
| 4 | **자기 DB만 쓴다.** 다른 시스템 데이터는 API로만 | 0023 |
| 5 | **보낼 것은 아웃박스에 먼저 적고, 받는 쪽은 멱등으로.** 성공할 때까지 재시도, 순서는 보장하지 않음 | 0014, 0025, 0043 |
| 6 | **결과를 모르면 정하지 않는다.** 확정 후 처리, 안 되면 사람에게 | 0003, 0021 |

## 3. 누가 무엇을 가지나

| 데이터 | 원본 | 다른 시스템 |
|---|---|---|
| 판매 · 판매 라인 | POS_APP | ERP가 아웃박스로 받음 |
| 결제 거래 (승인 · 취소 · 망취소) | Payment Server | POS는 결과만, ERP는 posTrx별 상태를 받음 |
| 상품 · 판매가 · 판매 중지 | ERP | 점포 서버는 자기 점포분 사본 |
| 재고 | ERP 재고 원장 | POS는 판매 결과만 보냄. 조회 · 쓰기는 ERP 화면 |
| 점포 · 기기 · 계정 | ERP | 점포 서버는 자기 점포분 사본 (PIN은 해시만) |
| 영업일 상태 · 기기의 그날 상태 | POS_APP | ERP는 받은 값을 씀 |
| 이상거래 | 발생: POS_APP / 처리 기록: ERP | |

## 4. 공통 규칙

| 규칙 | 내용 | ADR |
|---|---|---|
| 번호 | 거래번호 = 4자리(POS별, 거래 상태가 확정될 때만 증가). 거래 키 = `점포-영업일-POS-거래번호`. posTrx(결제 건 번호) = `거래 키-결제순번` (4-8-4-4-2). 거절 뒤 재결제는 같은 posTrx, 망취소 뒤 재결제는 다음 결제순번 | 0002, 0045 |
| 금액 | 원 단위 정수, 판매가는 부가세 포함, 부가세는 판매 단위로 한 번(원 미만 절사), 반품은 음수 | 0016 |
| 영수증번호 | 거래 키와 따로, `점포-발행일-POS-거래번호` (발행일 = 달력 날짜). Payment 운영 조회는 영업일 후보 2개로 찾음 | 0046 |
| 영업일 | 점포 단위, 점포 마감 → 개시로 전환 (자정 무관). 판매에 영업일 + 판매 확정 일시 | 0018 |
| 추적 ID | `X-REQUEST-ID`, 점포 서버가 만들고 Payment · ERP가 그대로 씀. 거래번호와 별개 | 0017 |
| 가격 확정 | 스캔 시점. 이후 재계산 없음 | 0034 |
| 카드 데이터 | 리더 SDK가 읽자마자 Payment 공개키로 암호화(봉투), POS 클라이언트 · 점포 서버는 중계만, Payment만 복호화. 전환 기간 뒤 평문 입력 끔 | 0006, 0050 |

## 5. 흐름별 핵심

**판매 · 결제**
- 판매를 `PENDING_PAYMENT`로 먼저 저장 → 결제 → 확정. 돈이 나갔는데 기록이 없는 경우는 구조상 없다.
- 결과 불명 → 조회 1회 → 그래도 모르면 자동 망취소. 망취소까지 실패하면 이상거래(확인 필요) (0003, 0021).
- 매장 즉시 보상은 없다. 시스템 문구는 짧게, 설명은 계산원이 한다 (0021).

**반품 (고객센터 POS에서만)**
- 반품 · 재판매는 고객센터 POS에서만 하고, 처리 담당자 사번을 기록 · 책임 (0031).
- 7일 이내(날짜 기준), 신선 · 조리 식품은 단순 변심 불가(하자 예외), 결제 카드 지참 필수 (0032, 0040).
- 부분 반품은 "전체 반품 + 원거래 연결 재판매(원래 가격)"로 대신한다 (0032).

**기준정보**
- 점포 마감 후 다음 영업일분 전체를 일배치로 받는다. 버전으로 맞춘다 (0034).
- 긴급 4종(판매 중지 · 가격 오류 · 계정 차단 · 기기 사용 중지)만 3분 폴링 (0034, 0035).
- 퇴사는 마지막 근무일 마감 후 반영. POS 로그인은 사번 + 4자리 PIN (0029).
- 거래번호는 점포 서버 체번 + 유니크 키. 같은 POS 번호를 다른 단말이 쓰고 있으면 기동 불가 (0044).

**마감 · 대사**

| 마감 | 누가 | ADR |
|---|---|---|
| POS 마감 → 점포 마감 (전 POS 마감 후, 미마감이면 다음 개시 차단) | 계산원 · 매장 관리자 | 0019 |
| ERP 일 대사 (T+1 배치, 불일치는 수기, 늦게 맞으면 자동 해소) | 자동 | 0027 |
| 점포 월마감 → 전사 월마감 (판매 수신 완료 필수, 돈 문제는 미결 이월) | 매장 관리자 → 본사 | 0033 |

모든 마감은 다시 열지 않는다. 틀린 것은 다음 영업일 · 다음 달의 조정으로 반영한다 (0041).

**이상거래 · 결제 문제**
- 대상: 돈이 빠졌지만 어떤 확정 판매에도 쓰이지 않은 승인. ERP 대사가 찾는다 (0025, 0027).
- 처리: 전산 담당자가 **ERP 화면에서** 운영 취소 요청 → Payment가 5분마다 가져가 검증 · 실행 (카드 불필요) (0040). 고객 반품은 카드 필수.
- 운영 취소 번호는 점포별 **운영 전용 POS**(기본 9999, 단말 기동 거부 · 마감 제외)로 Payment가 체번. Payment는 요청마다 **종료 신호**(완료 / 변경 없이 종료 + 사유 코드)를 보냄 (0047).
- 고객 문의 즉시 확인: 전산 담당자가 Payment 운영 조회 (0026).
- `MANUAL_REVIEW`: 담당자가 VAN · 카드사에 전화 · 메일로 확인 → ERP에서 운영 확정 요청 → Payment가 가져가 실행 → 필요하면 운영 취소 (0040).

## 6. 권한 (요약)

역할 4개: **계산원 · 매장 관리자(자기 점포) · 본사(전 점포) · 전산 담당자(본사 + 시스템 운영)**. 작업별 표는 ADR-0036.

## 7. 시스템별 할 일

| 시스템 | 할 일 | 근거 |
|---|---|---|
| **POS_APP** | 점포 서버 체계(영업일 · 마감 · 거래번호 체번), `INVENTORY` 제거, 기준정보 사본 · 일배치 · 3분 폴링, 판매 아웃박스, `X-REQUEST-ID` 생성 · 전파, 기기 유형 검사, 반품 규칙(고객센터 · 7일 · 반품 불가 · 카드 재읽기), PIN 로그인 · 잠금 | 0011~0019, 0029~0041 |
| **PAYMENT-SIMULATOR** | posTrx 새 형식 수용, posTrx별 합산 상태 아웃박스 전송(5분), 운영 조회 API, **운영 요청 수집 · 검증 · 실행**(운영 확정 · 운영 취소, 5분), Recovery 스케줄러 활성화, 알림 채널, **단말 암호화**(0050), **가맹점 ID · 터미널 ID 검증**(0048), **매입 · 정산**(0049), 부분 취소(확장) | 0002, 0021, 0025, 0026, 0040, backlog |
| **retail-erp** | 기준정보(상품 · 가격 · 점포 · 기기 · 계정) 원본과 배포 API, 판매 · 결제 상태 수신(멱등), 재고 원장, 일 대사 · 불일치 목록, 이상거래 처리 기록, 운영 요청 화면 · 대기 목록 API(Payment용), 2단계 월마감 · 귀속 마감월, 감사 로그 | 0007~0011, 0024~0041 |

각 시스템 안의 상세 설계(화면 · 테이블 · 내부 흐름)는 2단계에서 그 레포의 `docs/`에 둔다.

## 8. 주기 통신

시스템 사이에서 주기적으로 묻는 폴링은 세 개다: 긴급 변경 3분, 운영 요청 5분(가맹점 · 터미널 연결표 변경분을 함께 묻는다, 0048), 매입 제외 목록(준비될 때까지, 0049). v1은 폴링을 유지하고 웹소켓은 도입하지 않는다 (0042).

| 경로 | 방식 | 주기 | ADR |
|---|---|---|---|
| 점포 서버 → ERP 긴급 변경 4종 | 폴링 (생존 신호 겸용) | 3분 | 0034 |
| Payment → ERP 운영 요청 | 폴링 | 5분 | 0040 |
| Payment → ERP 가맹점 · 터미널 연결표 | 전체 + 변경분 | 하루 1회 + 5분 | 0048 |
| Payment → ERP 매입 제외 목록 | 폴링 (준비될 때까지) | 매일 05:00부터 30분 | 0049 |
| Payment → ERP 매입 결과 | 아웃박스 전송 | 5분 | 0049 |
| 점포 서버 → ERP 판매 · 반품 · 마감 요약 | 아웃박스 전송 (자기 DB 5초 확인) | 수시 | 0014, 0043 |
| Payment → ERP 결제 상태 | 아웃박스 전송 | 5분 | 0025 |
| 점포 서버 → ERP 기준정보 | 점포 마감 후 1회 | — | 0034 |

# ADR-0015 기준정보는 아침 일배치로 전체를 받고 긴급 변경은 폴링으로 받는다

- 상태: 대체됨 (ADR-0020)
- 날짜: 2026-11-18
- 관련 시스템: POS 클라이언트, POS_APP, ERP

## 맥락
- 상품 · 가격(ADR-0007), 점포 · 기기 · 계산원(ADR-0011)의 원본은 ERP이고, 각 점포 서버에 자기 점포분만 내려준다.
- 요청은 항상 점포 서버 → ERP 방향이다 (ADR-0013).
- 대부분의 변경은 다음 영업일부터 적용되면 되지만, 가격 오류 · 판매 중지 · 계정 차단처럼 당일 반영이 필요한 변경이 있다.

## 선택지
**일상 반영**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 아침 일배치로 전체 재수신 | 매일 원본과 다시 맞춰져 전날 어긋남이 스스로 복구됨. 현업에 흔한 구성 (**가정**) | 전체 데이터 전송량 |
| 변경분만 수시 반영 | 전송량 작음 | 한 번 어긋나면 계속 어긋남 |

**긴급 변경 수신**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 폴링 (예: 1분) | 연결을 유지하지 않음. 실패하면 다음 회차에 따라잡음. ERP는 점포 주소를 몰라도 됨 | 최대 1주기 지연 |
| 웹소켓 알림 | 거의 즉시 반영 | 점포마다 연결 유지 · 생존 신호 · 재연결 · 서버 간 연결 분배. 끊긴 동안 누락되므로 따라잡기 API가 어차피 필요 |

## 결정
- **버전:** ERP 기준정보 변경마다 점포별 변경 순번(버전)을 매긴다.
- **일배치:** 점포 서버가 정해진 시각에 ERP에서 자기 점포의 기준정보 **전체**를 받는다. 전체 데이터에는 "버전 N까지 반영"을 표시한다.
  - 시각: **영업일 마감 이후 · 개점 이전.** 구체 시각은 미정 — 영업일 정의와 함께 일마감 설계에서 정한다.
  - 적용: 임시 테이블에 모두 적재한 뒤 한 번에 교체한다. 실패하면 전날 데이터로 판매를 계속하고 알림을 보낸다.
  - 적용 직후 "버전 N 이후 변경분"을 한 번 받아, 배치 생성과 적용 사이의 긴급 변경을 놓치지 않는다.
- **긴급 변경:** 점포 서버가 **1분 주기 폴링**으로 "마지막 적용 버전 이후 변경분"을 받아 반영한다.
  - 긴급 대상: 가격 오류 정정 · 판매 중지 · 계정 차단(퇴사 · 분실). 그 밖의 변경(예정 가격 · 신규 상품 · 신규 계산원 등)은 일배치로 반영한다.
  - 긴급 변경도 ERP 원본을 고치므로 다음 일배치에 자연히 포함된다.
- **점포 서버 DB가 판매의 기준**이다. POS 클라이언트는 개점 시 점포 서버에서 오늘 데이터를 받아 화면을 구성한다. 판매 확정 시 가격은 점포 서버가 다시 계산하므로 클라이언트 화면이 잠시 옛것이어도 틀린 가격으로 판매되지 않는다.
- **웹소켓 알림은 확장**으로 둔다. 붙일 때는 같은 변경분 API 위에 "새 변경 있음" 알림만 얹는다.

## 대가와 후속 작업
- 긴급 변경이 POS 클라이언트 화면(예: 판매 중지 상품 버튼)에 반영되는 방식은 POS_APP 레포에서 정한다.
- 폴링 주기 · 일배치 실패 알림 기준, 긴급 대상의 최종 목록은 ERP 설계에서 확정한다.
- 계정 인증 정보 배포 방식은 미정 (ADR-0011 후속).
- 예정 가격(적용 시작 일시)을 둘지는 미정 (ADR-0007 후속).

# ADR-0012 POS_APP은 점포마다 서버를 두고 ERP · Payment Server는 본사에 둔다

- 상태: 결정
- 날짜: 2026-11-18
- 관련 시스템: POS 클라이언트, POS_APP, Payment Server, ERP

## 맥락
- v1 합격 기준은 대형점 1개 · POS 30대 동시 피크이고, 다점포(수십 개)는 확장을 막지 않는 설계 기준이다 (standards.md 2장).
- 기준정보는 ERP가 전 점포분을 갖고 각 점포에 자기 점포분만 내려준다 (ADR-0011). 판매 결과는 POS_APP에서 ERP로 올린다 (ADR-0009).

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| 점포 서버 (점포마다 POS_APP) | 본사 회선이 끊겨도 점포 안에서 판매 지속. 장애가 그 점포로 한정. 피크 응답이 다른 점포 부하와 무관 | 점포 수만큼 배포 · 업데이트 · 백업 · 모니터링. 버전 불일치 위험. 중앙 데이터는 전달 지연만큼 늦음 |
| 중앙 서버 하나 (전 점포 공용 POS_APP) | 배포 한 번, 데이터가 바로 중앙에 있음 | 본사 회선 · 서버 장애 시 전 점포 판매 중단. 전 점포 부하를 한 서버가 받음 |

대형 마트는 점포 서버, 소형 매장 · 프랜차이즈용 클라우드 POS는 중앙 구조가 흔하다는 구분은 일반적 경향으로 본 **가정**이다.

## 결정
- **POS_APP은 점포마다 서버 하나**를 둔다. 그 점포의 POS 클라이언트는 점포 서버에 붙는다.
- **ERP와 Payment Server는 본사에 하나씩** 둔다. 점포 서버 → Payment Server 호출은 본사 회선을 거친다.

```text
[점포 111]                                   [본사]
POS 클라이언트 ×30 ─▶ POS_APP 점포 서버 ─┬─▶ Payment Server ─▶ VAN
                                          └─▶ ERP (판매 결과 전달)
                      POS_APP 점포 서버 ◀──── ERP (111점 기준정보 배포)
```

- **본사 회선 장애 시:** 카드 결제는 Payment Server 연결 실패로 그 카드만 실패 처리하고 현금 판매는 계속한다 (ADR-0003). 판매 결과는 점포 서버에 남겨 두었다가 회선 복구 후 ERP로 올린다. 이 상태는 점포 서버가 살아 있으므로 **오프라인 판매가 아니다.**
- 점포 코드는 계속 모든 키에 포함한다. 점포 데이터를 본사 ERP에서 합칠 때 충돌을 막는다.

## 대가와 후속 작업
- standards.md 3.1의 오프라인 판매는 **점포 서버까지 장애인 경우**(POS 클라이언트가 서버 없이 판매)로 범위를 좁혀 읽는다.
- 점포 서버별 배포 · 버전 관리, 백업 · 모니터링(standards.md 장애 항목)은 점포 단위로 설계해야 한다.
- 점포 서버 → Payment Server 구간이 회선을 거치므로 ADR-0003 타임아웃 값에 회선 지연을 반영한다.
- **카페 키오스크의 배치는 미정**이다 (키오스크 설계 보류). 키오스크가 점포 서버에 붙을지 중앙에 붙을지 정할 때 이 구조를 막지 않도록, POS_APP API는 점포 서버 전제에 묶이지 않게 둔다.
- v1 검증 환경(compose)에서는 점포 서버 하나 + 본사 서버들로 구성한다.

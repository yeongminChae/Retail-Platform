# ADR-0038 판매에 쓰이지 않은 승인은 전산 담당자가 카드 없이 운영 취소하고 Payment가 ERP 반환 대상인지 확인한다

- 상태: 대체됨 (ADR-0040)
- 날짜: 2026-11-24
- 관련 시스템: POS_APP, Payment Server, ERP
- 대체: ADR-0037

## 맥락
- ADR-0037은 카드 취소에 결제 카드가 필요하다는 이유로, 판매에 쓰이지 않은 승인의 반환을 "고객이 카드를 가지고 오면 취소"로 두고 카드 없는 운영 취소를 두지 않았다. 고객이 오지 않으면 돈이 묶이는 한계가 있었다.
- PAYMENT-SIMULATOR 코드 확인 (2026-11-24, `main` `53f638d`):
  - `/cancel` 요청은 카드번호가 필수이며, Payment Server가 원승인 카드 fingerprint와 비교한다.
  - **Payment → VAN 취소 전문(`VanCancelTcpRequest`)에는 카드번호가 없다.** 원 VAN 거래 ID · 원승인번호 · 금액으로 취소한다.
  - 즉 카드번호는 VAN이 요구하는 값이 아니라 Payment Server 입구의 본인 확인 정책이다.
- 현업에서 VAN사 가맹점 관리 화면으로 원승인 정보 기준 취소를 하는 방식과 비슷하다 (**가정**).
- 카드 없는 취소의 악용 위험은 "실제 판매에 쓰인 승인을 취소해 고객이 상품과 돈을 모두 가져가는 공모"다. 돈은 원래 카드로만 돌아간다.
- 반환 대상("돈이 빠졌지만 어떤 확정 판매에도 쓰이지 않은 승인")은 ERP 일 대사가 찾는다 (ADR-0025 · 0027).

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| 카드 필수 유지 (ADR-0037) | 카드 없는 취소 없음 | 고객 미방문 시 반환 불가 |
| 운영 취소 + 2인 승인 | 단독 악용 방지 | 두 번째 사람이 형식적 승인이 되기 쉬움. 실제 대조 대상(반환 대상인가)은 시스템이 확인할 수 있는 정보 |
| **운영 취소 + 1인 실행 + 시스템 검증 + 감사** | 공모 대상(판매에 쓰인 승인)을 시스템이 차단. 빠름 | Payment → ERP 조회 API 추가. ERP가 살아 있어야 실행 가능 |
| 운영 취소 + 1인 실행 + 감사만 | 구현 최소 | 공모를 사후에만 발견 |

## 결정
- **고객 반품은 결제 카드 지참 필수** (ADR-0037 유지). 결제 포기 시 보상 취소는 카드를 다시 읽는다 (유지).
- **판매에 쓰이지 않은 승인의 반환은 운영 취소로 한다.**
  - Payment Server에 **운영 취소** 경로를 둔다. 카드 확인을 건너뛰고, 저장된 원승인 정보로 VAN에 취소한다.
  - **전산 담당자 1인**이 요청 · 실행한다 (ADR-0036).
  - **시스템 검증:** Payment Server는 실행 전에 **ERP에 해당 승인(posTrx + 시도 순번)이 반환 대상 목록에 있는지 조회**한다. 없으면 거부한다. Payment → ERP 요청이므로 요청 방향 원칙(ADR-0024)을 지킨다.
  - **감사:** 요청자 · 사유 · ERP 처리 건 번호 · 결과를 감사 로그에 남긴다. 정기 사후 검토는 운영 절차로 둔다.
  - 2인 승인은 두지 않는다.
- 고객센터 POS의 별도 "결제 반환" 메뉴는 두지 않는다 (본사에서 운영 취소로 반환).
- **처리 기록 (유지):** ERP에 처리 완료 여부 · 담당자 · 처리 업무(예: 운영 취소 / 조치 불필요 / 기타) · 메모 · 일시를 저장하고 감사 로그를 남긴다. 운영 취소 결과는 Payment 결제 상태 전송(ADR-0025)으로 ERP에 반영되어 다음 대사에서 불일치가 해소된다.

## 대가와 후속 작업
- PAYMENT-SIMULATOR 과제: 운영 취소 API(전산 담당자 권한), 실행 전 ERP 반환 대상 조회, 감사 로그.
- ERP 과제: 반환 대상 조회 API (Payment Server용, 응답만).
- 운영 취소는 ERP가 응답할 수 있을 때만 실행된다 (운영 작업이라 지연 허용).
- 원승인이 아직 결과 불명(`UNKNOWN_TIMEOUT`)인 건은 취소가 아니라 망취소 대상이다. `MANUAL_REVIEW` 건의 처리는 별도로 정한다.

# ADR-0024 ERP는 다른 시스템을 호출하지 않고 받기만 한다

- 상태: 결정
- 날짜: 2026-11-20
- 관련 시스템: POS_APP, Payment Server, ERP

## 맥락
- 점포 서버 → ERP는 이미 한 방향이다 (ADR-0013). ERP는 판매 결과를 받고(ADR-0014), 기준정보 요청에 응답만 한다(ADR-0020).
- 이상거래 처리와 결제 대사를 위해 ERP가 Payment Server의 결제 상태를 알아야 한다 (ADR-0021, 0022). 처음 안은 ERP가 Payment Server API를 조회하는 것이었다.
- 시스템 관계를 ERP가 맨 위에 있고 다른 시스템이 ERP로 보고하는 구조로 본다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| ERP는 받기만 하고, 다른 시스템이 ERP로 보냄 | 요청 방향이 전부 → ERP 하나. ERP가 다른 시스템 장애에 묶이지 않음. 수신은 아웃박스 + 멱등 패턴 하나로 통일 | 보내는 쪽이 ERP 주소 · 재전송을 알아야 함. 실시간 조회 불가 |
| ERP가 필요할 때 다른 시스템을 조회 | 실시간. 보내는 쪽 변경 없음 | ERP가 다른 시스템 가용성에 의존. 요청 방향이 섞임 |

## 결정
- **ERP는 다른 시스템을 호출하지 않는다.** 다른 시스템의 요청에 응답하고, 보내온 데이터를 받기만 한다.
- 데이터는 각 시스템이 **아웃박스 + 백그라운드 전송**으로 ERP에 보내고, ERP는 **멱등으로 수신**한다 (ADR-0014와 같은 패턴).
- 다른 시스템 데이터는 API로만 접근한다는 원칙(ADR-0023)은 그대로다. 접근 방향이 "보내는 쪽 → ERP"로 정해질 뿐이다.

```text
점포 서버 ──(판매 결과, 아웃박스)──▶ ERP ◀──(결제 상태, 아웃박스)── Payment Server
점포 서버 ──(기준정보 요청)────────▶ ERP   (응답만)
```

## 대가와 후속 작업
- ERP 화면에 보이는 다른 시스템 데이터는 전송 주기만큼 늦다.
- ADR-0021 · 0022에서 "ERP가 Payment Server `MANUAL_REVIEW`를 모은다"는 결정은 그대로이며, 수집 경로는 Payment Server의 전송(ADR-0025)으로 한다. ADR-0022 후속 작업의 "Payment Server 목록을 가져올 때"는 "Payment Server가 보내온 데이터를 보여줄 때"로 읽는다.

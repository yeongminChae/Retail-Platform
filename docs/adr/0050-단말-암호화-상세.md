# ADR-0050 단말 암호화는 POS PC의 카드 리더 시뮬레이터가 Payment 공개키로 봉투를 만들고, POS 화면 · 점포 서버는 중계만 한다

- 상태: 결정
- 날짜: 2026-11-28
- 관련 시스템: POS 클라이언트, POS_APP, Payment Server
- 관련: ADR-0006 (2단계 상세)

## 맥락
- ADR-0006은 2단계로 "카드 리더가 읽자마자 Payment 공개키로 암호화, POS_APP은 암호문 + BIN만 중계하고 키가 없음, Payment가 복호화"를 정했다. 승인 API 변경과 키 관리(처음엔 설정 파일 키 쌍, 한계로 명시)를 후속으로 남겼다.
- 플랫폼 목표는 바로 상용화할 수 있는 상태이며, 카드 데이터 보호 범위에서 POS 쪽을 빼는 것이 목표다.
- 정할 것: 암호 방식, 봉투 형식, 공개키를 POS 쪽에 주는 경로, 리더를 누가 만드는지, 평문 입력에서 옮기는 방법.

## 선택지
| 항목 | 선택지 | 장점 | 단점 |
|---|---|---|---|
| 암호 방식 | RSA-OAEP-256 + AES-256-GCM | 표준 라이브러리만으로 구현, 널리 알려짐 | 키가 김 |
| | ECDH + AES-GCM (ECIES) | 키가 짧음 | 구현 · 설명이 더 어려움 |
| 개인키 보관 | 키스토어 파일 + 키 교체 | 로컬에서 바로 됨 | 서버 파일에 키 (한계) |
| | Vault | 상용 구조에 가까움 | 구성 · 테스트 복잡 |
| 리더 | POS PC의 카드 리더 시뮬레이터 (PAYMENT-SIMULATOR) | 현업 구조(단말 연동 프로그램)를 흉내. POS 화면이 카드번호를 모름 | 작은 프로그램 하나 추가 |
| | 브라우저 WebCrypto (POS 화면 안) | 설치 없음 | POS 화면이 카드번호를 받음. HTTPS 필수 |
| | Java SDK 라이브러리 | 형식 주인과 한 레포 | POS 클라이언트가 Java가 아니면 못 씀 |

## 결정
- **암호 방식:** 매번 새 AES-256 키로 카드 데이터(PAN · 유효기간)를 AES-GCM으로 암호화하고, 그 키를 Payment RSA 공개키로 감싼다(RSA-OAEP-256).
- **봉투(`encryptedCard`):** 버전 · 키 ID · 감싼 키 · IV · 암호문, 그리고 평문으로 **BIN 8자리 · nonce · 발급 시각**. BIN · nonce · 시각은 GCM AAD로 암호문에 묶어 바꿔치기를 막는다. 형식은 PAYMENT-SIMULATOR `docs/phase2/09-단말-암호화.md`에 언어 무관하게 고정한다.
- **POS 클라이언트 · 점포 서버는 봉투를 그대로 중계한다.** 열 수 없고 BIN만 읽을 수 있다. 끝 4자리 · 마스킹 번호는 지금처럼 Payment 응답으로 받는다.
- **리더는 PAYMENT-SIMULATOR의 `card-reader-simulator`**다. POS PC에서 도는 작은 프로그램으로, POS 화면이 `localhost`로 "이 금액 카드 읽어 줘"를 요청하면 테스트 카드로 봉투를 만들어 돌려준다. **POS 화면은 카드번호를 모른다.** 현업의 단말 연동 프로그램 구조를 흉내 낸 것이다 (가정).
- **공개키 배포:** Payment가 공개키 목록(키 ID · 공개키 · 만료 · 사용 중 여부)을 API로 주고, **점포 서버가 받아 캐시해 카드 리더 시뮬레이터에 내려준다** (점포 서버 → Payment, 요청 방향 원칙 유지). 기동 시와 하루 1회 갱신한다.
- **개인키:** Payment 키스토어 파일(키 ID별), 비밀번호는 환경변수. 교체는 "새 키 추가 → 1일 뒤 사용 전환 → 다시 1일 뒤 이전 키 폐기".
- **재전송 방지:** 발급 시각 ± 5분, nonce는 posTrx와 묶어 저장한다. 같은 nonce + 같은 posTrx는 멱등 재요청으로 허용하고, 다른 posTrx면 거부한다.
- **전환:** Payment는 당분간 평문 카드 입력과 봉투를 둘 다 받는다. POS 화면이 카드 리더 시뮬레이터로 옮긴 뒤 플랫폼 실행 환경에서 평문 입력을 끈다.
- 표현은 ADR-0006대로 "PCI DSS 원칙을 참고한 카드 데이터 보호 설계"로 쓴다.

## 대가와 후속 작업
- 개인키가 Payment 서버 파일에 있다 (알려진 한계). KMS · HSM · Vault 이전은 확장으로 둔다.
- Payment → VAN 구간의 PAN 보호는 범위 밖이다. 실제로는 VAN 규격의 구간 암호화가 있다고 본다 (가정).
- 실제 단말이 BIN을 평문으로 함께 넘기는지는 VAN마다 다를 수 있다 (ADR-0006 가정 유지).
- POS_APP 과제: POS 화면이 카드 리더 시뮬레이터를 호출, 점포 서버의 공개키 캐시 · 배포, 승인 · 반품 카드 확인 요청을 봉투로 전환, 1단계 테스트(점포 서버에 PAN 없음)를 봉투 기준으로 유지.
- POS 화면 기술과 무관하다 (`localhost` HTTP 호출만). 클라이언트는 가볍게 만든다.
